# 模块说明：每个文件负责什么、为什么这么分

这份文档解释代码结构背后的取舍。看懂它之后，改一个功能应该能立刻知道该动哪个文件。

---

## 1. 分层的唯一原则：核心层不依赖 Qt

```
        ui/           PyQt5 界面：只负责画和收触摸事件
         │             （唯一允许 import Qt 的地方）
         ▼
      app.py         WoodPulseApp：把下面这些接起来，GUI 只跟它说话
         │
    ┌────┼────────┬──────────┬─────────┬──────────┐
    ▼    ▼        ▼          ▼         ▼          ▼
capture  platform_  storage  telemetry  selfcheck  update
  │      client       │         │          │         │
  │        │          └─────────┴──────────┴─────────┘
  ▼        ▼                    全部只用标准库 + psutil
adapters/  contracts.py
camera     （字段与事件类型的单一来源）
replay
```

**为什么坚持这条**：`python tests/test_acceptance.py` 里 49 项验收用例
（H01–H16）**一个 Qt 都不需要**，在没有屏幕、没有 X 的机器上就能跑完。
界面只在最后一步被验证（`tools/ui_shots.py` 渲染成 PNG 逐页核对）。
如果核心层 import 了 Qt，"能不能跑"就和"有没有屏幕"绑在一起，
CI 和现场预检都做不了。

`ui/qt.py` 是唯一的例外处理点：它同时支持 PyQt5 与 PySide6，
并保证 `HAVE_QT=False` 时 import 不抛异常 —— 这样 `--headless` 与验收脚本
在同一套代码里成立。

## 2. 逐个模块

### `contracts.py` —— 词汇表

平台信封、能力取值、来源标识、事件类型清单、样例包格式、批次目录清单都在这里。
其它模块**只引用这里，不自己造字段名**。

关键的几个定义：

- `Capability`：`live` / `replay` / `unavailable` / `preset`。
  界面上的每个数据源都必须能回答它属于哪一种。
- `SourceMode`：界面角标用的文案（「相机实拍」「检测样例」「无数据」「预制结果」）。
- `EventType`：终端会发出的**全部**事件类型。
  平台侧据此核对白名单 —— 至少保证"能收下"或"显式拒收"二者之一（见 §4 第 6 条）。
- `EVENT_BATCH_CONTRACT_NOTE`：把 PRD 没写清楚的一条定死 ——
  `accepted` / `duplicated` 是 **messageId 数组而不是计数**。
- `Command`：白名单六条；`ReceiptState`：三态。
- `null_field(reason)`：不可用字段的标准写法。

### `app_state.py` —— 状态机，替代散落的布尔量

旧版把"是否连接""是否在扫描""是否升级完成"散成若干布尔量，界面和线程各改一份，
暂停后收到旧回调就复活了。这里把状态收敛成显式迁移表：

| 状态机 | 转移要点 |
|---|---|
| `TaskMachine` | `finished` / `interrupted` 是终态，**不接受旧的 resume**（H05） |
| `BatchMachine` | `open → sealed` 之后才允许上传；`partial` 可以续传（H10） |
| `ConfigMachine` | `received → confirmed → applied`，确认差异才回 ack（H09） |
| `UpdateMachine` | `verified → staged → applying → applied/rolled_back`（H11） |
| `ConnectionMachine` | `online / degraded / offline`（§8.2 的 5s/15s 阈值） |

`AppState.validate_command()` 是命令准入的唯一入口：白名单 → 过期 → 任务版本 →
批次匹配四项检查，任一项不过就回 `failed` 并给错误码（H08）。

`Notifier` 是极简发布订阅：GUI 把它桥接成 Qt 信号，测试里直接收回调。

### `telemetry.py` —— 真实遥测，文件里没有随机数

PRD §6 表格逐行对应。三条硬规则：

1. **不可用就返回 null + reason**，不填 0、不填估计值。
   `cpu_percent` 第一次调用永远返回 0，所以首样本标 `quality=warmup` 而不是报 0。
2. **网卡速率是差分**：`(bytes_now - bytes_prev) / 单调时间差`。
   计数回退（重连、接口重置）时重建基线并返回 0，不出负值也不出巨大峰值。
3. **能力探测**：`probe_capabilities()` 按启动检查生成能力表，
   IMU / 电池 / GPU 探不到就是 `unavailable`。

能力探测的细节：温度走 `vcgencmd` → sysfs thermal → psutil 三级探测并**记录来源**；
降频读 `get_throttled` 并把**当前标志与历史标志分开**；
CPU 频率只报频率、不当负载。

### `storage.py` —— SQLite、批次目录、outbox

**线程模型（这是踩过的坑）**：`sqlite3` 连接默认只能在创建它的线程用，
而平台客户端跑在独立网络线程上（PRD §10 要求网络与 GUI 事件循环隔离）。
所以按线程各持一个连接 + 一把可重入锁串行化写。
只加 `check_same_thread=False` 是不够的 —— 那样多线程会同时用同一个 cursor，
出的是更隐蔽的错乱。

**写盘顺序固定**：数据文件 → marks/segments/quality/result → `manifest.json`（原子替换）。
manifest 一旦落地就表示"这批数据完整"，之后才允许上传。
`commit_manifest()` 顺带算出 `datasetHash`（对包内除 manifest.json 外所有文件
按路径字典序拼 `path\0sha256\n` 再取 sha256），终端与平台用同一算法核对。

**崩溃恢复**：`recover_interrupted()` 把上次 bootId 下仍是 `open` 的批次标为中断态。
已保存帧数**从 frames.csv 实际数出来**，不用库里的计数字段 ——
库里那个值每积累若干帧才同步一次，崩溃时必然偏小，直接报给界面就是低报了保住的数据。

### `platform_client.py` —— HTTP + 手写 WebSocket

只依赖标准库：`urllib` 做 HTTP（流式分片上传），`socket` 手写 RFC6455 客户端。
这样树莓派上 apt 装完 PyQt5 与 psutil 就不需要再 pip 装东西。

两条只有真跑起来才会暴露、必须写对的规则：

1. **失败必须退避**。上传失败如果立刻重试，一秒能打几百次平台，日志刷爆、电量耗光。
   每个作业记 `attempts` 并按 1、2、4…秒指数退避（带抖动）。
2. **失败不能卡住队首**。旧实现遇到失败就 `return`，后面的文件永远排不上，
   表现是"有一部分文件怎么都传不上去"。

还有两条业务规则：`accepted` 只表示已接收（`executed` 由真正完成动作的地方回）；
关键业务事件**在正常连接期间**也要周期性 flush，不能只在重连那一刻补传 ——
否则平台会看到"命令已下发但没有回执"。

### `capture.py` —— 采集编排

`CaptureController.tick(dt)` 是唯一的推进入口，GUI 每 100ms 调一次。
三条性质：

- 回放推进**只由运行/暂停/结束控制**。暂停时 `advance()` 直接返回空列表，
  这是"暂停冻结"的实现点（H05）。
- 标记**不暂停**任务，取当前相机截图 + 样例帧号 + 单调时间。
  截图失败也保留标记并标「缺图」，不伪装成完整记录（H07）。
- 方向由操作者选定；没选就只记「标记 01」，**不猜方位**。

`BatchManager.finalize()` 负责落盘顺序与 manifest 原子提交。

### `selfcheck.py` —— 逐项自检

十项，顺序固定：平台连接、相机可读、样例包、存储空间、环境配置、
控制器能力、IMU、电池、GPU、应用版本。

关键是**四态分明**：`ok` / `warn` / `fail` / `unavailable`。
`unavailable` 表示"本机根本没有这个能力"，不算阻断项 —— 不让"没有 IMU"
拦住整个现场作业，但界面上必须是灰的，**不全绿**。

### `update.py` —— 演示模型包

主线：接收通知 → 实际下载 → 实际摘要检查 → 切换本地演示模型版本 →
重启对应软件任务 → 回验。

刻意不做的事：不改真实 ESP32 固件版本字段；没有 VBUS/MUX 检测代码就不显示
"已检测供电""总线自动移交"；摘要只由本机重新计算得出（点空白处不产生任何通过事件）；
采集进行中只暂存。

回验的口径写得很明确：本机**不执行神经网络推理**，
所以回验内容是"包版本、输入规格、示例输出与采集配置的一致性核对"，
而不是编一个准确率出来。

### `adapters/` —— 两个数据源

`camera.py`：单一采集源（整个程序只有一个线程打开设备），
帧是带时间戳的 `bytes`（跨线程传递安全），`stop()` 有明确的
"置退出标志 → 等线程结束 → release"流程。
缩放**只做等比**，`scale_bgr()` 保证 16:9 不会被拉伸（H16）。

`replay.py`：本机唯一的"回波"来源。逐帧读盘而不是一次性加载，
这样"暂停冻结"在实现上天然成立；数据只读，重复排练必然得到相同帧内容（H06）。
`downsample()` 按**最大值**抽取：窄的异常峰在均值下会被邻近平掉，现场看到的"响应区"就消失了。

### `scenarios.py` —— 剧本口径的单一来源

三套样例包的登记表，以及 0.71 / 0.84 / 0.87 这组数值、适用域检查帧号、
暂停作用范围说明。界面与测试都从这里取，避免各处硬编码后对不上。

### `ui/` —— 灰银色 800×480

`theme.py` 的颜色表直接照抄 PRD §4.1，不做"更有科技感"的自由发挥。
尺寸按 800×480：顶部 44px、主体 344px、底部 68px，主按钮 64px、次级 48px
（`test_screen_budget_adds_up` 会断言这三个数加起来正好是 480）。

`widgets.py` 全部自绘，不引入图表库：
响应序列图是逐列追加的二维强度图，`QPainter` 直接画最快；
相机预览严格等比；日志默认折叠在底部条里，不占主画面。

**布局上的一个反复踩到的坑**：800×480 的主体只有 344px 高，
面板里多放两行键值对，Qt 不会滚动也不会报警，而是**把行压到一起造成文字重叠**。
所以各页的键值对行数都有上限（环境页 5 行、作业页摘要 5 行），
长信息放 Tooltip。改这些页面时留意这一点。

### `app.py` —— 总装

`status_snapshot()` 是"设备现在到底什么状态"的单一出口，
界面读它、`query_status` 命令回它、诊断包存它。
`handle_command()` 是平台命令的唯一入口：先回 `accepted`，
再做校验与执行，最后回 `executed` 或 `failed`。

## 3. 数据与文件命名

```
batches/<batchId>/
  manifest.json    批次清单 + datasetHash（原子提交，落地即可上传）
  config.json      本批次绑定的配置快照
  frames.csv       frame_index,sample_index,amplitude,t_ms（逐帧追加）
  segments.json    逐帧响应段（峰值、质量、配对图像）
  marks.json       人工标记权威记录（marks.csv 是人可读副本）
  quality.json     帧完整性、饱和、空帧、缺帧说明
  result.json      端侧结论（withheld / none / preliminary）
  plan.json        采集计划（测区与路径）
  dataset.json     物理样本分组（参考样本采集才有）
  events.log       阶段事件（NDJSON）
  session-events.json  本次会话事件
  images/          标记截图（frame_00000.png）
  images/index.json    图像索引
```

帧标识统一 5 位：`frame-00250` / `frame_00250.png`。
样例包与实机批次用同一口径，将来互相引用不会对不上。

## 4. 踩过的坑（都是真跑起来才暴露的）

这几条都已在代码里修掉，并写在这里以免被改回去。

1. **SQLite 跨线程使用**。平台客户端线程一启动就 `ProgrammingError` 死掉，
   而平台侧因为 socket 还开着，仍显示设备在线 —— 表现是"遥测一直不来、命令收不到"。
   修法：按线程持有连接 + 写路径加锁。

2. **关键事件只在重连时 flush**。`command.accepted/executed` 这类事件在
   WebSocket 正常连接期间一条都发不出去，平台侧表现为"命令 delivered=true
   但永远没有回执"。修法：`_pump()` 里每 0.5 秒周期 flush。

3. **上传失败不退避**。实测 45 秒内对平台打了 572 次同一个文件的创建请求。
   修法：指数退避 + 失败作业移到队尾，不卡住后面的文件。

4. **空摘要建单被平台拒**。`register_file` 在某些路径下会写入空 sha256，
   而平台创建上传时要求 64 位摘要，表现为"最后一个文件永远传不上去"。
   修法：`upload_files()` 对空摘要现场重算并回填。

5. **`device.selfcheck` 与"永久拒收"标记**。平台若按未知类型静默丢弃、
   又不把 messageId 放进 `accepted` / `rejected`，终端无法 ack，
   会每 0.5 秒无限重推同一份报告。修法（两端一起改）：
   把它写进 `EventType`；`rejected` 每条带 `messageId` + `retryable`；
   平台保证每个 messageId 最终进 `accepted` 或 `rejected` 之一。
   终端按 `retryable` 分流（false 出队 / true 退避重试 / 缺省按 true），
   并对"发出去却既未确认也未拒收"的情况计数告警（`_unaccounted_attempts`）。
   回归用例在 `tests/test_event_rejection.py`。

6. **`--config` 在配置文件读取之后才解析**。示例配置看似加载成功，
   实际整份被忽略、全用默认值，而且没有任何报错 —— 部署时最难查的一类问题。
   修法：`_extract_config_path()` 先单独扫一遍命令行，配置文件优先读。
   回归用例在 `H16TouchLayout.test_config_file_and_cli_precedence`。

7. **崩溃恢复低报已保存帧数**。库里那个计数每积累若干帧才同步一次，
   崩溃时必然偏小，直接报给界面就是低报了保住的数据。
   修法：`count_frames_on_disk()` 从 `frames.csv` 实际数出来。
   回归用例在 `H14CrashRecovery`。

## 5. 想改功能时该动哪里

| 想做的事 | 改这里 |
|---|---|
| 平台地址/令牌/心跳间隔 | `docs/config.example.json`（不用改代码） |
| 换相机设备或后端 | 配置 `camera.device` / `camera.backend` |
| 改界面配色或字号 | `ui/theme.py`（颜色表与尺寸常量） |
| 加一个遥测字段 | `telemetry.py` 采集 + `contracts.TELEMETRY_KEYS` + `status_page` 显示 |
| 加一条平台命令 | `contracts.Command` 白名单 + `app.py` 的 `_cmd_xxx` + 回执测试 |
| 换一套检测样例 | 改 `samples/` 内容 + `scenarios.py` 的登记表 |
| 加一个页面 | `ui/` 下新建 page + `shell.py` 的 `NAV_ITEMS` 与 `_wire_signals` |
| 接真实雷达驱动 | 新增 `adapters/radar_live.py` 并在 `telemetry.probe_capabilities` 里改能力声明 |
| 接真实固件烧录 | 新增 `services/deployment_adapter`（首版刻意不含烧录路径） |
