# 木脉智检 · 设备接入接口说明（v1.0 / 对齐手持端 PRD §7.4）

本文是**手持终端与平台之间的接口契约**，逐接口列出：方法、路径、认证、请求字段、响应字段、错误码、幂等规则。
字段名一律 **lowerCamelCase**，与 `F:\1\pi5\woodpulse\contracts.py` 完全一致；实现以
`F:\1\pi5\tools\mock_platform.py`（本地模拟平台）为准，冒烟测试 `F:\1\pi5\tools\smoke_mock_platform.py`
对每个接口都有真实调用与断言。

配套文档：`F:\1\pi5\docs\平台接入教程.md`（怎么把终端接到你们真平台、怎么排查）。

约定读法：

* **认证**列写"设备令牌"，指 `X-Device-Token: <deviceToken>`（也接受 `?deviceToken=` / `?token=` / 请求体 `deviceToken`；
  WS 另见 §2.2）。真平台建议**只认一种**并写进自己的文档，见 §6 歧义清单第 6 条。
* **错误响应**统一沿用现有平台的形状（`F:\1\平台deepseek\server\api\http.mjs` 的 `sendError`）：

  ```json
  {"code": "OFFSET_MISMATCH", "message": "偏移不连续：期望 offset=200，收到 300",
   "fieldErrors": [], "retryable": true, "expected": 200, "actual": 300}
  ```

  `retryable=true` 表示"退避后重试有意义"，`false` 表示"重试也没用，先改请求"。
  部分错误会在顶层带业务附加字段（如 `expected` / `actual` / `receivedOffset` / `size`）。

* **时间**一律 UTC ISO-8601 带 `Z`，毫秒精度（`2026-09-12T15:53:01.664Z`）。设备 `sentAt` 只用于同机排序，
  传输时延要用平台侧 `receivedAt` 或心跳往返测，见教程 §6.1。
* **单位**：百分比 0—100、字节、秒或毫秒、摄氏度；UI 再做 KB/s、MB/s 换算（PRD §7.3）。
* **ID 形态**：`deviceId` 形如 `handheld-02`；`messageId` = `msg-<12hex>`；`commandId` = `cmd-<12hex>`；
  `uploadId` = `up-<12hex>`；`artifactId` = `art-<12hex>`；`receiptId` = `rcpt-<12hex>`；
  `fileId` = `file-<uuid4>`（与现有平台 `server/services/assets.mjs` 生成的 `file-<uuid>` 同形，便于适配层互换）。

## 1. 消息信封与公共字段

### 1.1 上行信封（终端 → 平台）

所有上行事件（WS 文本帧或 `device-events/batch` 数组元素）都是同一个信封，定义在 `contracts.Envelope`：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `schemaVersion` | string | 是 | 信封主版本，当前 `"1.0"`。**主版本不认识要拒收**（PRD §7.3），平台回 `unsupported_schema_version(<v>)` 或 422 `UNSUPPORTED_SCHEMA` |
| `messageId` | string | 是 | 全局唯一，平台按它去重（至少一次投递的幂等键） |
| `deviceId` | string | 是 | 设备身份。与信封所属设备不一致时拒收（`device_id_mismatch`） |
| `bootId` | string | 是 | **一次进程启动一个**。用于区分"重启"与"同一次运行内的重连"；平台遇到新 bootId 要重置该设备的任务版本与旧连接 |
| `seq` | int | 是 | 在一次 `bootId` 内单调递增。只用于丢旧帧/查缺口，不当作全局顺序 |
| `sentAt` | string | 是 | 设备侧发送时间（UTC ISO-8601 带 Z）。**不能用来算传输时延**（设备时钟未校准） |
| `demoSessionId` | string | 是 | 排练轮次（`demo-01`）。平台按它做轮次隔离，重开一轮不该污染上一轮数据 |
| `type` | string | 是 | 事件类型，见 §1.5 清单 |
| `payload` | object | 是 | 事件体。不同 `type` 结构不同 |

```json
{

    "network": {"interface": "wlan0", "address": "192.168.1.42", "linkUp": true,
                "txBytesPerSec": 42000, "rxBytesPerSec": 18000, "isWireless": true},
    "camera": {"backend": "v4l2", "device": "/dev/video0", "captureFps": 24.8,
               "displayFps": 15.0, "droppedFrames": 0, "lastFrameAgeMs": 80, "state": "ok", "reason": null},
```

遥测 payload 的字段清单以 `contracts.TELEMETRY_KEYS` 为准（PRD §6 一行一个）。
**不可采集的字段必须是 `null` / `supported:false` / `quality:"unavailable"` 并带 `reason`**（`contracts.null_field`），
`0` 表示有效零值——不得用 0 或随机数顶替（PRD §6）。

### 1.2 下行命令帧（平台 → 终端，WS）

定义见 `mock_platform.CommandRecord.frame()`，PRD §8.1 要求命令体含
`commandId` / `expectedTaskRevision` / `targetBatchId` / `expiresAt` / `payload`：

| 字段 | 类型 | 必有 | 说明 |
|---|---|---|---|
| `kind` | string | 是 | 固定 `"command"`，用于与业务事件区分 |
| `schemaVersion` | string | 是 | `"1.0"` |
| `messageId` | string | 是 | 这一帧的唯一 ID（与 commandId 不同：重推同一命令时 messageId 会变） |
| `deviceId` / `bootId` | string | 是 | 目标设备与目标 `bootId`；**bootId 不是当前 boot 时应拒绝执行**（重启前的命令） |
| `seq` | int | 是 | 平台侧序号，单调递增，用于丢旧帧 |
| `sentAt` | string | 是 | 平台发送时间 |
| `demoSessionId` | string | 是 | 排练轮次 |
| `type` | string | 是 | 命令名，白名单见 §3.3 |
| `commandId` | string | 是 | 命令幂等键。**回执必须带它**；同 commandId 重复下发不得重复执行 |
| `expectedTaskRevision` | int\|null | 是 | 平台期望的任务版本。与设备当前版本不符 → 回 `failed` + `revision_stale` |
| `targetBatchId` | string\|null | 是 | 命令只作用于该批次；不匹配 → `failed` + `batch_mismatch` |
| `expiresAt` | string | 是 | 过期拒绝执行（`failed` + `command_expired`）。到期判定要按平台时钟，别用设备未校准时钟 |
| `issuedAt` | string | 是 | 下发时间 |
| `actorId` | string | 是 | 操作人（与 deviceId 分开，PRD §7.1） |
| `payload` | object | 是 | 命令参数；**同时镜像了上面四个定位字段**（`commandId`/`type`/`expectedTaskRevision`/`targetBatchId`/`expiresAt`），因为终端 `platform_client._handle_inbound()` 只把 `payload` 交给命令处理器。顶层为权威值 |

```json
  "deviceId": "handheld-02",

  "seq": 3,
  "sentAt": "2026-09-12T15:53:10.503Z",
  "demoSessionId": "demo-01",
  "type": "pause_capture",
  "commandId": "cmd-45167b616ceb",
  "expectedTaskRevision": 3,
  "targetBatchId": "scan-Z04-002",
  "expiresAt": "2026-09-12T15:58:10.503Z",
  "issuedAt": "2026-09-12T15:53:10.503Z",
  "actorId": "manager",
  "payload": {
    "commandId": "cmd-45167b616ceb",
    "type": "pause_capture",
    "expectedTaskRevision": 3,
    "targetBatchId": "scan-Z04-002",
    "expiresAt": "2026-09-12T15:58:10.503Z",

  }

```

### 1.3 回执（终端 → 平台，WS 上行）

回执是普通信封，`type` 取 `command.accepted` / `command.executed` / `command.failed`，
`payload` 里带 `commandId` 与 `state`：

| 字段 | 类型 | 必须 | 说明 |
|---|---|---|---|
| `commandId` | string | 是 | 对应命令 |
| `state` | string | 是 | `accepted` / `executed` / `failed`（`contracts.ReceiptState`） |
| `scope` | string | 建议 | 作用范围，如 `local_capture`；暂停类命令必须写清楚（PRD §5.3） |
| `errorCode` | string | failed 必填 | `contracts.ErrorCode` 之一：`batch_mismatch`/`revision_stale`/`command_expired`/`unsupported`/`not_ready`/`terminal_state`/`scope_limited`/`checksum_failed`/`io_error` |
| `reason` | string | failed 必填 | 人可读原因，现场排障就靠它 |
| `result` | object | 可选 | executed 时的结果摘要 |
| `at` | string | 建议 | 回执生成时刻（UTC ISO-8601） |

```json
{"schemaVersion": "1.0", "messageId": "msg-9a1c...", "deviceId": "handheld-02",
 "bootId": "boot-49d9a1ac716b", "seq": 109, "sentAt": "2026-09-12T15:53:10.707Z",
 "demoSessionId": "demo-01", "type": "command.executed",
 "payload": {"commandId": "cmd-45167b616ceb", "state": "executed",
             "scope": "local_capture", "reason": "本地采集/回放已停止推进",
             "at": "2026-09-12T15:53:10.707Z"}}
```

**三态语义（PRD §8.1，平台不得越级）**：

* `accepted` = 已收到、正在处理；平台**不能**据此把设备状态标成"已执行"；
* `executed` = 设备真正完成了动作（本地已经停、文件已经落盘、版本已经读回）；
* `failed` = 带 `errorCode` 与 `reason`。平台只凭"消息发出成功"就当成功是明确禁止的。

### 1.4 WS 控制消息（平台 → 终端）

| `kind` | 何时发 | 关键字段 |
|---|---|---|
| `hello` | 设备通道升级成功后立刻 | `schemaVersion`、`deviceId`、`bootId`、`demoSessionId`、`heartbeatIntervalMs`、`offlineAfterMs`、`configVersion`、`platformTime`、`pendingCommandCount`、`payload.platformConfig`（终端 `platform_client` 读它填本地通道参数） |

### 1.5 `type` 清单（上行事件类型）

平台按 `type` 分派，取值来自 `contracts.EventType`（两端的共同词表）：

| 分组 | 取值 |
|---|---|
| 设备 | `device.register`、`device.hello`、`device.telemetry`、`device.health`、`device.capabilities` |
| 采集 | `capture.started`、`capture.paused`、`capture.resumed`、`capture.finished`、`capture.mark_created`、`capture.progress`、`capture.anomaly` |
| 批次 | `batch.finalized`、`batch.upload_started`、`batch.upload_completed` |
| 配置 | `config.received`、`config.applied` |
| 回执 | `command.accepted`、`command.executed`、`command.failed` |
| 更新 | `update.downloaded`、`update.verified`、`update.applied`、`update.failed` |
| 系统 | `system.recovered`、`system.error` |
| **扩展类型** | `device.selfcheck`（启动自检报告）。已写入 `contracts.EventType`，平台两侧都应对齐 |

**未知 `type` 的处理**：模拟平台给出 `rejected[].reason = "unknown_type(<type>)"` 且
`retryable = false`，同时在 WS 上回一条 `{"kind":"warning","code":"UNKNOWN_TYPE"}`。

拒收**不等于**可以不管：被拒的 `messageId` 必须**出现在 `rejected` 里**，
终端才能把它从 outbox 里删掉。早期实现只回 `reason`、不回 `messageId`，
结果是终端既不确认也不出队 —— 每 0.5 秒重推一次 `device.selfcheck`，而平台侧
只看到"设备在刷屏"。现在的规则是：

> 平台对每个收到的 `messageId`，最终必须给出 `accepted` 或 `rejected` 二者之一。
> `rejected` 里带 `messageId` + `retryable`；`retryable=false` 时终端直接出队。

`device.selfcheck` 的两条路径都要能演示（见 §4.4）：

```bash
python tools/mock_platform.py --port 8099                      # 收下（默认）
python tools/mock_platform.py --port 8099 --reject-extra-types  # 显式拒收，retryable=false
```

## 2. 设备注册与设备通道

### 2.1 `POST /api/devices/register`

| 项 | 值 |
|---|---|
| 认证 | 设备令牌（`X-Device-Token`）；**令牌错必须 401**，不能因为 deviceId 眼熟就放行 |
| 成功码 | `200` |
| 幂等 | 同 `(deviceId, bootId)` 重复注册不新建记录、`registeredAt` 不变；`bootId` 变了视为重启（刷新 `registeredAt`、任务版本归零、旧 WS 连接作废） |

请求字段（`contracts.build_register_payload()` 生成）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `schemaVersion` | string | 是 | `"1.0"` |
| `deviceId` | string | 是 | 设备号 |
| `bootId` | string | 是 | 本次启动 ID |
| `appVersion` | string | 是 | 终端应用版本（`2.0.0-demo`） |
| `adapterVersion` | string | 是 | 端侧适配器版本（SCANNER_ADAPTER_VERSION） |
| `modelVersion` | string | 是 | 当前演示模型版本 |
| `operatorId` | string\|null | 否 | 操作人（actorId）。与 deviceId 分开 |
| `host` | object | 否 | `{hostname, machine, platform, python}`，排障用 |
| `startedAt` | string | 否 | 进程启动时刻 |
| `capabilities` | object | 是 | 由**启动检查**生成（PRD §7.2）：`{"camera":"live","radar":"replay","imu":"unavailable","battery":"unavailable","telemetry":"live"}`，取值只能是 `live`/`replay`/`unavailable`/`preset` |
| `capabilityReasons` | object | 否 | 不可用原因的逐项说明，如 `{"imu":"没有 IMU 硬件"}` |

响应字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `deviceId` | string | 回显 |
| `registeredAt` | string | 平台登记的注册时刻（同 bootId 重复注册时取首次） |
| `heartbeatIntervalMs` | int | 心跳间隔，`5000`（PRD §8.2） |
| `offlineAfterMs` | int | 判离线阈值，`15000` |
| `configVersion` | string | 当前应生效的环境配置版本，`"CFG-02"` |
| `demoSessionId` | string | 本设备的排练轮次，`"demo-01"` |
| `platformTime` | string | 平台当前时间（用于校时/判断 `expiresAt`） |

错误码：

| 状态 | code | retryable | 触发条件 |
|---|---|---|---|
| 401 | `UNAUTHORIZED` | false | 令牌缺失或不匹配 |
| 422 | `NO_DEVICE_ID` / `NO_BOOT_ID` | false | 缺必填字段 |
| 422 | `UNSUPPORTED_SCHEMA` | false | `schemaVersion` 主版本不认识 |
| 422 | `BAD_CAPABILITIES` | false | `capabilities` 不是对象 |
| 422 | `BAD_JSON` | false | 请求体不是合法 JSON 对象 |
| 413 | `BODY_TOO_LARGE` | false | 请求体超限（模拟平台 8 MiB） |
| 503 | `REGISTER_REJECTED` | **true** | 平台维护中：终端应退避重试（模拟平台 `--fail-register` 注入） |

### 2.2 `WS /ws/devices/{deviceId}`

| 项 | 值 |
|---|---|
| 路径 | 只占 `/ws/devices/{deviceId}`；**浏览器用的 `/ws`（`server/services/hub.mjs`）不要复用**，两者房间语义不同 |
| 升级 | 标准 RFC6455：`Upgrade: websocket`、`Connection: Upgrade`、`Sec-WebSocket-Key`、`Sec-WebSocket-Version: 13`；服务端回 `101` + `Sec-WebSocket-Accept = base64(sha1(key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))` |
| 认证 | 四选一：`?deviceToken=`（终端现有写法）/ `?token=` / `X-Device-Token` 头 / `Sec-WebSocket-Protocol: woodpulse.v1, auth.<token>`。**认证失败必须在 101 之前回 401**，终端才能区分"握手被拒"和"连上后被踢" |
| 子协议 | 客户端给 `woodpulse.v1` 时服务端回显它；不给也能连 |
| 帧 | 只收文本帧 JSON；客户端帧必须带掩码；单帧上限 8 MiB（超 → close `1009`） |
| 保活 | 服务端空闲 20 s 发 WS ping；终端回 pong 即可。终端也有 5 s 应用层心跳（`device.health`） |
| 关闭 | 收到 close 要回 close；服务端对端关闭/超时按 `--ws-ping-interval` × 2 判"假活"并断开 |
| 连接即补发 | 连上后平台**重推所有"未回执且未过期"的命令**（至少一次投递）；终端按 `commandId` 幂等，绝不能因为收到两次就执行两次 |

错误码：`426 UPGRADE_REQUIRED`（不是升级请求）、`426 BAD_WS_VERSION`（版本不是 13）、`400 NO_WS_KEY`、`401 UNAUTHORIZED`。

### 2.3 `GET /api/devices/{id}/state`（调试用）

| 项 | 值 |
|---|---|
| 认证 | 模拟平台免鉴权（**调试接口**；真平台应要求操作员角色） |
| 成功码 | `200` / 未知设备 `404 NO_DEVICE` |

响应字段（用于人工联调时"平台上到底看到了什么"）：

| 字段 | 说明 |
|---|---|
| `deviceId` / `bootId` / `registeredAt` / `registerCount` | 身份 |
| `connectionState` | `online`（有活跃设备 WS 连接）/ `degraded`（没有连接，但最后一次上行还在 `offlineAfterMs` 以内）/ `offline`（超过 `offlineAfterMs` 没有任何上行） |
| `lastSeenAt` / `websocketClients` | 最后一次上行时刻与连接数 |
| `appVersion` / `adapterVersion` / `modelVersion` / `operatorId` / `host` | 注册信息 |
| `configVersion` / `taskRevision` / `currentBatchId` | 平台侧认为的当前状态 |
| `capabilities` / `capabilityReasons` | 能力表 |
| `lastDemoSessionId` | 最后一次上行信封里的轮次（与平台轮次不同会告警） |
| `lastTelemetry` / `lastEvent` / `lastReceipt` | 最近一条完整信封（遥测取最新一份，不堆历史） |
| `commands[]` | 已下发命令：`commandId`/`type`/`expectedTaskRevision`/`targetBatchId`/`expiresAt`/`delivered`/`deliveryAttempts`/`expired`/`receipt` |
| `pendingCommands[]` | 未回执的命令子集 |
| `previews[]` | 最近保留的预览图元数据（`frameIndex`/`bytes`/`sha256`/`receivedAt`） |
| `counters` | `telemetry`/`events`/`eventsDuplicated`/`commands`/`receipts` 计数，联调时一眼看出"哪条链路没通" |
| `authFailures` / `lastAuthFailure` | 令牌错了几次、最近一次是什么，专门用来查 401 |

> 模拟平台还有 `GET /api/devices`（设备列表）与 `GET /api/health` 的 `devices.detail`，
> 都是**模拟平台调试扩展**，真平台不要求实现。

## 3. 命令

### 3.1 `POST /api/devices/{id}/commands`

| 项 | 值 |
|---|---|
| 认证 | 操作员令牌（真平台应走 `Authorization: Bearer <登录令牌>` + 角色权限，`server/services/permissions.mjs`）；模拟平台也接受设备令牌方便脚本调用 |
| 成功码 | **`202 Accepted`**（已受理，不等于已执行） |
| 幂等 | 带同一个 `commandId` 重复提交 → 返回已保存的那条命令、`replayed:true`、**不重复下发**（PRD §8.1） |

请求字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `type` | string | 是 | 命令名，必须在白名单内 |
| `commandId` | string | 否 | 幂等键；不传由平台生成 |
| `expectedTaskRevision` | int | 否 | 期望任务版本。不传时：**平台已派发过任务**就用平台记录的版本（旧命令会被设备拒绝，H08）；**从没派发过任务**则不带版本校验（`null`），因为平台没有版本信息可比 |
| `targetBatchId` | string | 否 | 目标批次；不传用该设备当前批次（`assign_task` 用 payload 里的 `batchId`） |
| `payload` | object | 否 | 命令参数（见 §3.2） |
| `ttlMs` | int | 否 | 有效期，默认 `300000`；用于制造"过期拒执"场景 |
| `expiresAt` | string | 否 | 直接指定绝对过期时刻（UTC ISO-8601）。调试用：可以下发一条**已经过期**的命令来验证终端回 `failed` + `command_expired`（PRD §13 H08）；给了它就忽略 `ttlMs` |

> `assign_task` 会由平台推进任务版本：新版本写进 `payload.taskRevision`，终端 `_cmd_assign_task` adopt 它，
> 两边从此对同一个 revision 达成一致（否则平台以为版本是 0、终端本地是 1，后续每条命令都会被
> `revision_stale` 拒掉——这是实测踩过的坑）。

响应字段：`commandId`、`type`、`deviceId`、`expectedTaskRevision`、`targetBatchId`、`expiresAt`、`issuedAt`、
`delivered`（是否已送到在线连接）、`connectionState`、`replayed`、`note`。

**幂等规则**：`commandId` 是唯一幂等键。同一 commandId 的第二次请求返回第一次的结果（HTTP 200/202 都一样），
平台不重复推送。终端侧的对应规则是：同 commandId 第二次到达不得重复执行，回已保存的回执。

错误码：`401 UNAUTHORIZED`、`422 NO_COMMAND_TYPE`（缺 type）、`422 BAD_REVISION`（版本不是整数）、
`422 UNSUPPORTED_COMMAND`（不在白名单，响应里带 `allowed` 列表）。

设备离线时**仍然受理**：返回 202、`delivered:false`、`connectionState:"offline"`，命令入队，设备重连后重推。

### 3.2 命令白名单与 payload（PRD §8.1）

| `type` | 用途 | payload 关键字段 |
|---|---|---|
| `assign_task` | 派发任务 | `orderId`、`projectId`、`componentId`、`zoneId`、`zoneIds[]`、`batchId`、`scenarioId`、`configVersion`、`modelVersion` |
| `apply_config` | 应用环境配置 | `configVersion`、`airTempC`、`relativeHumidityPct`、`windSpeedMs`、`source`、`publishedAt`、`publishedBy` |
| `pause_capture` | 请求暂停采集 | `reason`、`scope`（如 `local_capture`）、`requestedBy`、（可选）`batchId` |
| `request_upload` | 请求上传 | `batchId`、`reason`、`priority`、`includePreview` |
| `prepare_update` | 准备更新 | `artifactId`、`artifactKind`、`packageType`、`demoOnly`、`version`、`previousVersion`、`sha256`、`size`、`downloadUrl`、`fileId`、`target` |
| `query_status` | 查询状态 | `includeHealth`、`includeUpload`、`reason` |

**明确不在白名单里的**：任意 shell、任意文件路径、任意下载 URL、远端 `start`/`resume`（需要本机确认，PRD §8.1）。
模拟平台对非白名单命令一律 422，`run_shell` 这类请求是冒烟测试里的负例。

`pause_capture` 的作用范围必须在回执里说清楚：它只停**本地采集任务/回放推进**，
不代表真实雷达停止发射（那要专用驱动确认）。范围受限时回 `failed` + `scope_limited`。

### 3.3 过期与版本冲突

| 场景 | 终端应回 | 平台侧表现 |
|---|---|---|
| `expiresAt` 已过 | `failed` + `errorCode:"command_expired"` | 命令记录 `expired:true`；模拟平台控制台 `expire <deviceId>` 可把未回执命令的 `expiresAt` 改成过去并重推一次 |
| `expectedTaskRevision` 与设备当前版本不符 | `failed` + `revision_stale` | 平台发新命令前先 `query_status` 或从 `assign_task` 结果取新版本 |
| `targetBatchId` 与当前批次不符 | `failed` + `batch_mismatch` | 设备只作用于匹配批次 |
| 任务已进终态（finished/interrupted） | `failed` + `terminal_state` | 旧 resume 一律拒绝 |

## 4. 事件补传

### 4.1 `POST /api/device-events/batch`

| 项 | 值 |
|---|---|
| 认证 | 设备令牌 |
| 用途 | 断线后补传**关键业务事件**（PRD §8.2 至少一次投递）。遥测不进这个接口，掉线期间只保留最新一份 |
| 幂等 | 按 `messageId` **全局去重**；重复提交同一批只会命中 `duplicated`，不重复入库 |

请求字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `deviceId` | string | 否* | *可推断：请求体 → `X-Device-Id` 头 → 事件信封里的 `deviceId` → 设备专属令牌 → 平台只注册了一台设备时取它。**真平台建议强制显式传**（见 §6 第 7 条） |
| `bootId` | string | 否 | 当前启动 ID |
| `events` | array | 是 | 信封数组，单次最多 **500** 条 |

响应字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `deviceId` | string | 实际归属设备 |
| `accepted` | string[] | **入库成功的 messageId 列表** |
| `duplicated` | string[] | **去重命中的 messageId 列表** |
| `acceptedCount` / `duplicatedCount` / `rejectedCount` | int | 上面几个列表的长度（便于人读与断言） |
| `rejected` | array | `[{"messageId": "...", "reason": "...", "code": "...", "retryable": false}]` |
| `unaccounted` | string[] | 契约自检：**既未接受也未拒收**的 messageId。正常情况下必须为空 |
| `receivedAt` | string | 平台接收时刻 |
| `note` | string | 语义提示 |

> ⚠️ `accepted`/`duplicated` 用 **messageId 列表**（不是计数）：终端 `platform_client._post_events_batch()`
> 直接把它们当成"可以 ack 的 ID 列表"。PRD §7.4 没规定类型，这里按终端实现定，另附 `*Count` 计数。
> 真平台若返回计数，终端 ack 逻辑会失效——见 §6 第 1 条。

**三条平台侧必须遵守的规则：**

1. **`accepted` / `duplicated` 是 messageId 数组，不是计数。** 终端要靠这些 ID 在本地 outbox 里
   精确标记"已确认"。只回计数时终端只能按发送顺序猜，一旦有事件被拒就会错位、重复投递。
2. **每个收到的 messageId 最终必须进入 `accepted` 或 `rejected` 之一，不得静默丢弃。**
   不支持的类型（例如平台暂时没有实现 `device.selfcheck`）不能既不确认也不拒收 ——
   终端拿不到确认会按重试节奏无限重推同一份报文（实测每 0.5 秒一次）。
3. **`rejected` 每条必须带 `messageId` 与 `retryable`：**

   | `retryable` | 含义 | 终端行为 |
   |---|---|---|
   | `false` | 永久拒收：重试多少次结果都一样 | **直接出队，不再重试** |
   | `true` | 临时失败：过一会儿可能就好 | **保留在 outbox 并按退避重试** |
   | 缺省 | 语义不明 | 按**临时失败**处理（保守：宁可多试也不丢业务数据） |

`rejected[].reason` / `code` 取值与可重试性的对应关系：

| `code` | `reason` 形态 | `retryable` | 什么时候用 |
|---|---|---|---|
| `unknown_type` | `unknown_type(device.selfcheck)` | `false` | 平台没实现这个事件类型 |
| `unsupported_schema_version` | `unsupported_schema_version(9.0)` | `false` | 信封主版本不认识（PRD §7.3 要求拒收） |
| `device_id_mismatch` | `device_id_mismatch(handheld-09)` | `false` | 信封里的设备号与连接身份不符 |
| `missing_message_id` | `missing_messageId` | `false` | 没有 messageId，无从去重 |
| `missing_type` | `missing_type` | `false` | 信封不合法 |
| `not_an_object` | `not_an_object` | `false` | 数组元素不是对象 |
| `queue_full` / `server_busy` | `queue_full` | `true` | 平台侧临时过载 |

错误码：`401 UNAUTHORIZED`、`413 TOO_MANY_EVENTS`（>500，retryable）、`422 NO_EVENTS`（events 不是数组）、`422 NO_DEVICE_ID`、`422 BAD_JSON`。

```json
{"deviceId": "handheld-02",
 "accepted": ["msg-b40a753ea6b3"], "duplicated": [],
 "acceptedCount": 1, "duplicatedCount": 0,
 "rejected": [
   {"messageId": "msg-88afeeaec9e6", "reason": "unknown_type(device.selfcheck)",
    "code": "unknown_type", "retryable": false}
 ],
 "rejectedCount": 1, "unaccounted": [],
 "receivedAt": "2026-09-12T15:53:10.487Z",
 "note": "按 messageId 去重；rejected 每条带 retryable：false=永久拒收（终端出队），true=临时失败（终端重试）。"}
```

模拟平台提供开关来分别演示这两条路径：

```bash
# 默认：收下契约未定义的类型（打一行提示，推动两端补齐契约）
python tools/mock_platform.py --port 8099

# 演"平台暂不支持 device.selfcheck"：显式拒收 + retryable=false
python tools/mock_platform.py --port 8099 --reject-extra-types
```

两条路径都验证过：终端在收到 `retryable=false` 后立刻出队，之后不再重推；
收到 `retryable=true` 时保留并按退避重试，平台恢复后重试成功才出队。

## 5. 文件、批次、产物

### 5.1 `POST /api/files/uploads`（创建/续传）

| 项 | 值 |
|---|---|
| 认证 | 设备令牌 |
| 成功码 | `201`（新建）/ `200`（续传或复用已完成） |
| 幂等 | 业务键 = `(deviceId, name, batchId, role, sha256)` |

请求字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `name` | string | 是 | 文件名（basename）。角色与媒体类型由它推断 |
| `size` | int | 是 | 整文件字节数 |
| `sha256` | string | 是 | 整文件摘要，**64 位十六进制小写** |
| `batchId` | string | 否 | 所属批次 |
| `role` | string | 否 | 文件角色。取值见 §5.6 |
| `mediaType` | string | 否 | 不传按扩展名推断 |
| `deviceId` / `bootId` | string | 否 | deviceId 可推断（同 §4.1） |
| `demoSessionId` | string | 否 | 排练轮次 |

响应字段：`uploadId`、`deviceId`、`name`、`size`、`sha256`、`role`、`batchId`、`mediaType`、
`receivedOffset`（**续传起点**）、`completed`、`reused`、`fileId`、`chunkSizeHint`、`expiresAt`、`platformTime`；
响应头 `X-Upload-Id`。

**两种"不用传了"的短路（PRD §9.2）**：

1. 同一业务键有**未完成**的上传 → 返回原 `uploadId` 与当前 `receivedOffset`，从断点续传；
2. 平台上已有**同 sha256 的已完成文件** → 新 `uploadId` + `completed:true` + `reused:true` + 同一个 `fileId`。
   注意：**仍要建立本次业务关联**（新 uploadId 记在本次 batchId 下），不是"直接忽略"。

错误码：

| 状态 | code | 说明 |
|---|---|---|
| 401 | `UNAUTHORIZED` | 令牌问题 |
| 422 | `NO_NAME` / `NO_SIZE` / `BAD_SIZE` | 缺名字、缺大小、大小为负 |
| 422 | `BAD_SHA256` | 不是 64 位十六进制小写 |
| 409 | `UPLOAD_CONFLICT` | 同设备同批次同名同角色但摘要不同 → 先改名或清理旧上传（带 `existingUploadId`/`expected`/`actual`） |

### 5.2 `PUT /api/files/uploads/{id}/chunks`（写分片）

| 项 | 值 |
|---|---|
| 认证 | 设备令牌 |
| 偏移 | `?offset=<int>` **或** `X-Chunk-Offset: <int>` 头（二者都收；终端现有实现用头） |
| 分片摘要 | `X-Chunk-Sha256: <hex>`（可选；给了就校验） |
| 请求体 | **裸字节**，`Content-Length` 必须准确 |

响应字段：`uploadId`、`receivedOffset`（写完后新的偏移）、`size`、`duplicated`、`completed`、`chunkSha256`、`platformTime`。

**幂等规则**：

* 重复分片（`offset < receivedOffset`）且磁盘上那一段字节与本次一致 → `200` + `duplicated:true`，`receivedOffset` 不变；
* 同一位置内容不同 → `409 CHUNK_CONFLICT`（拒绝覆盖）；
* `offset > receivedOffset` → `409 OFFSET_MISMATCH`（响应带 `expected`/`actual`/`receivedOffset`/`size`）；
* 上传已完成后再发分片 → `200` + `duplicated:true` + `completed:true`，不再落盘。

错误码：`404 NO_UPLOAD`、`409 OFFSET_MISMATCH`/`CHUNK_CONFLICT`、
`422 NO_OFFSET`/`BAD_OFFSET`/`EMPTY_CHUNK`/`CHUNK_OVERRUN`/`CHUNK_CHECKSUM_MISMATCH`、`400 SHORT_BODY`（分片没收完连接就断）。

**故障注入**：`--drop-after-bytes N` 时，模拟平台在累计收到 N 字节后**不发响应直接掐断 TCP**（日志 `status=499`）。
已写入的字节保留，`receivedOffset` 如实推进——终端应重新 `POST /api/files/uploads` 拿到新的 `receivedOffset` 再继续。

### 5.3 `POST /api/files/uploads/{id}/complete`（收尾校验）

| 项 | 值 |
|---|---|
| 认证 | 设备令牌 |
| 请求 | `{"sha256": "...", "size": 300}`（都可选，默认用创建时的声明） |
| 幂等 | 已完成再 complete → 同一个 `fileId`，`replayed:true` |

响应字段：`uploadId`、`fileId`、`name`、`bytesConfirmed`、`sha256`、`declaredSha256`、`mediaType`、`batchId`、`role`、`completedAt`、`replayed`、`platformTime`。

**核心规则**：服务端**重算整文件 sha256** 再与声明比对（PRD §7.4）。不一致一律 `422`：

```json
{"code": "CHECKSUM_MISMATCH", "message": "服务端重算摘要与声明不一致，整文件不可信，请重传",
 "fieldErrors": [], "retryable": true, "uploadId": "up-55b998d9b510",
 "expected": "d392499814638640e6d8a6dacf225731c2056ffbc53010bb9d4d2c40f1e3a7b1",
 "actual": "284cee429fdd0b1d1b93ea2f5d4c1a2f4c8e0a7b6d5c4b3a2918f7e6d5c4b3a2",
 "size": 300, "receivedOffset": 300}
```

> 例中两个摘要是示意值；真实响应里的 `expected` 就是你声明的摘要，`actual` 是平台按收到的字节实算的摘要。
> 这两个字段是终端判断"要不要整文件重传"的依据，缺一个都不行。

错误码：`404 NO_UPLOAD`、`409 UPLOAD_INCOMPLETE`（带 `receivedOffset`/`size`，retryable）、`422 CHECKSUM_MISMATCH`。
模拟平台 `--reject-checksum` 会在 complete 前**真的翻转服务端落盘文件的 1 个字节**，用来验证终端的失败分支——不做假报错。

### 5.4 `POST /api/batches`（提交 manifest 与 fileIds）

| 项 | 值 |
|---|---|
| 认证 | 设备令牌 |
| 幂等 | 业务键 = `batchId`；同内容重复提交 → `replayed:true`；内容不同 → `409 BATCH_CONFLICT`（不允许原地改写） |

请求字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `batchId` | string | 是 | 批次号，两端与样例包必须指向同一个 |
| `fileIds` | array | 是 | 元素两种形态都接受：`"file-..."` 字符串，或终端实际发的对象 `{"fileId","role","path","sha256","bytes"}` |
| `files` | array | 否 | manifest 自带的清单 `[{"role","path","bytes","sha256"}]`（终端 `storage.commit_manifest` 生成） |
| `expectedFiles` | array | 否 | 平台侧显式要求的清单 `[{"name","role"}]`；`name` 以 `/` 结尾表示目录项（如 `images/`），只要有 image 角色文件就算满足 |
| `datasetHash` | string | 否 | 数据集摘要，算法见下 |
| `deviceId` | string | 否 | 可推断（同 §4.1） |
| 其它 manifest 字段 | any | 否 | 平台**不校验也不丢弃**未知字段，原样收下并在 `platformAck` 里回显给设备。PRD §9 的样例字段名是 `projectId`/`orderId`/`componentId`/`zoneId`/`configVersion`/`modelVersion`/`scenarioId`/`format`/`radarSourceMode`/`cameraSourceMode`/`pairing`；终端 `BatchRecord.to_manifest()` 另会带 `sourceMode`/`samplePackage`/`responseSequenceSource`/`datasetHash`/`files` 等，命名以终端为准、平台不应硬编码 |

**"应当交付的清单"取三处并集**：`expectedFiles` ∪ `files[].path` ∪ `fileIds[].path`；三者都没有才退回 PRD §9 的必需文件清单
（`manifest.json`/`config.json`/`marks.json`/`segments.json`/`frames.csv`/`quality.json`）。
比对时**同时按文件名与相对路径匹配**（终端上传只传 basename，而清单写的是 `images/frame_00000.png`）。

响应字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `batchId` / `deviceId` | string | 回显 |
| `accepted` | bool | 批次是否被受理（清单本身合法） |
| `complete` | bool | **整批是否收全**（`missing` 与 `unknownFileIds` 都为空才为 true） |
| `missing` | array | `[{"name","role","reason":"not_uploaded","source":"manifest.files"}]` |
| `receivedFiles` | array | `[{fileId,name,size,sha256,mediaType,role,batchId,path}]` |
| `unknownFileIds` | string[] | 平台查不到的 fileId（终端应重传，或说明该文件从未上传成功） |
| `receivedBytes` / `fileCount` | int | 统计 |
| `batchState` | string | `uploaded`（收全）/ `partial`（部分接收，`contracts.BatchState`） |
| `datasetHashMatch` | bool\|null | 平台重算 `datasetHash` 的结果（未声明则为 null） |
| `datasetHash` / `actualDatasetHash` | string | 声明值 / 平台实算值 |
| `archiveCheck` | object | `{requiredFiles, missingRequired, note}`：PRD §9 归档必需清单的**提示性**检查，不改变 `complete` |
| `submittedAt` / `replayed` / `note` | — | 语义提示 |

`datasetHash` 算法（与终端 `storage.commit_manifest()` 一致）：把清单内每个文件的
`path + "\0" + sha256 + "\n"` 按 `path` 字典序拼起来取 sha256，**不含 `manifest.json`**。
不一致说明缺件或内容被改过；模拟平台只报告不拦截，真平台建议视为整批不可信。

**部分接收语义（PRD §9.2）**：`complete:false` 时该批**不得进入整批分析**，`batchState="partial"`。

错误码：`401 UNAUTHORIZED`、`409 BATCH_CONFLICT`、`422 NO_BATCH_ID`/`BAD_FILE_IDS`/`BAD_EXPECTED_FILES`/`NO_DEVICE_ID`。

### 5.5 `GET /api/artifacts/{id}/manifest`（产物清单）

响应字段：`artifactId`、`artifactKind`、`packageType`、`demoOnly`、`target`、
`version`、`previousVersion`、`sha256`、`size`、`fileId`、`mediaType`、`downloadUrl`、`releasedAt`、`contents[]`、`notes[]`。

| 字段 | 说明 |
|---|---|
| `artifactKind` | `demo_nonflashable` = **不可烧录的演示包**（平台 PRD §11.3）。真固件包是另一套分支 |
| `packageType` | `demo_package` / `model_package` / `firmware_package` |
| `demoOnly` | `true` 时终端**不得**调用任何烧录工具、不得改写控制器固件版本字段 |
| `target` | `{"deviceId","deviceModel","controller","flashable":false}` |
| `downloadUrl` | 相对路径（如 `/api/files/file-xxx/download`），终端拼 `platformUrl` 后下载 |
| `notes[]` | 人可读注意事项（例："SHA-256 只证明完整性，不证明发布者身份"） |

错误码：`401`、`404 NO_ARTIFACT`。

### 5.6 `GET /api/files/{id}/download`（真实字节）

| 项 | 值 |
|---|---|
| 响应 | **裸字节**（不是 JSON）；与现有平台 `server/api/http.mjs` 的同名接口一致 |
| 响应头 | `X-File-Sha256`（终端下载后必须核对）、`X-File-Id`、`Accept-Ranges: bytes`、`Content-Disposition` |
| Range | 只支持单段：`bytes=start-end`、`bytes=start-`、`bytes=-suffix` → `206` + `Content-Range: bytes start-end/size` |
| 错误码 | `404 NOT_FOUND`、`410 GONE`（文件已不在磁盘）、`416 BAD_RANGE`（格式非法，带 `Content-Range: bytes */size`）、`416 RANGE_NOT_SATISFIABLE`（越界） |

更新包下载必须"边下边算 sha256"，与 `X-File-Sha256` 比对上才算下载成功；不一致要重下（PRD §8.2、H11）。

### 5.7 `POST /api/artifacts/{id}/receipts`（产物回执）

请求字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `commandId` | string | 是 | 对应的 `prepare_update` 命令。**幂等键**：同 commandId 重复提交返回同一个 `receiptId` |
| `deviceId` | string | 否 | 可推断 |
| `sha256` | string | 否 | 设备自己算出的下载件摘要；平台会与登记的产物摘要比对，不一致 → `409 ARTIFACT_CHECKSUM_MISMATCH`（带 `expected`/`actual`） |
| `downloadVerified` | bool | 否 | 下载+摘要校验是否通过 |
| `applyResult` | string | 是 | `applied` / `failed` / `skipped` |
| `versionReadBack` | string | 否 | 应用后从本机读回的版本（回验，不能只报"成功"） |
| `previousVersion` | string | 否 | 失败时要退回的版本 |
| `errorCode` / `reason` | string | 否 | 失败时必填（`checksum_failed`/`io_error` 等） |
| `steps` | array | 否 | `[{"step","ok","at","detail"}]`：下载/校验/切换/回验逐步留痕 |
| `startedAt` / `finishedAt` | string | 否 | 时间窗 |

响应字段：`receiptId`、`deviceId`、`artifactId`、`commandId`、`sha256`、`downloadVerified`、`applyResult`、
`versionReadBack`、`previousVersion`、`errorCode`、`reason`、`steps`、`startedAt`、`finishedAt`、`acceptedAt`、`replayed`。

错误码：`404 NO_ARTIFACT`、`409 ARTIFACT_CHECKSUM_MISMATCH`、`422 NO_COMMAND_ID`/`BAD_APPLY_RESULT`/`NO_DEVICE_ID`。

### 5.8 `POST /api/devices/{id}/preview`（低帧率预览图）

| 项 | 值 |
|---|---|
| 传输编码（本文**定这一种**） | 请求体 = **一张裸 JPEG**；`Content-Type` 用 `image/jpeg` 或 `application/octet-stream` 都接受 |
| 必有头 | `X-Frame-Index: <int>`（必须能对上是第几帧） |
| 可选头 | `X-Captured-At`（采集时刻）、`X-Frame-Sha256`（帧摘要） |
| 可选 query | `batchId` |
| 保留策略 | 每台设备只保留最近 N 张（模拟平台 `--preview-keep`，默认 10）；**不作为原始图像归档**，原图仍在批次目录里 |
| 成功码 | `202` |

响应字段：`deviceId`、`frameIndex`、`bytes`、`sha256`、`batchId`、`capturedAt`、`receivedAt`、`keptFrames`、`retentionLimit`、`note`。

错误码：`401`、`413 FRAME_TOO_LARGE`（>2 MiB，预览应下采样）、
`422 NO_FRAME_INDEX`/`BAD_FRAME_INDEX`/`EMPTY_FRAME`/`NOT_JPEG`（缺 `FF D8` SOI）/`FRAME_CHECKSUM_MISMATCH`。

## 6. 与现有平台接口的映射（PRD §7.4 最后一段）

现有平台指 `F:\1\平台deepseek\server\`（Express 风格 + `ws`）。

| 手持端接口 | 现有平台对应 | 处理方式 | 复用时必须保持一致的语义 |
|---|---|---|---|
| `POST /api/files/uploads` + `PUT .../chunks` + `POST .../complete` | 平台 PRD §14.2 的 `POST /uploads`、`PUT /uploads/{id}/chunks/{n}`、`POST /uploads/{id}/complete`；磁盘侧已有 `services/assets.mjs`（流式写盘 + 边写边算摘要） | **适配层新增分片语义**：现有 `POST /api/files`（`?name=` 裸 body、一次性、无断点、无幂等）不能被直接复用 | `fileId` 语义（一次上传登记一个文件；同摘要复用仍要建立本次业务关联）、sha256 十六进制小写、`receivedOffset` 单调不回退、`409` = 偏移/状态冲突、`422` = 字段或阶段错误 |
| `GET /api/files/{id}/download` | **已实现**：`server/api/http.mjs` 的 `route("GET", "/api/files/:id/download")`，返回真实字节 + `x-file-sha256` + `Content-Disposition` + Range 由 Node 端处理 | **可直接复用路径与响应头**；但它 `auth:true`（要登录令牌）且会写"产物已下载"业务记录 | 设备令牌要能通过适配层鉴权；**设备下载不能被写成"操作员取用产物"**（那会把设备固件拉取记成人工动作）；`X-File-Sha256` 必须保留 |
| `GET /api/files/:id` / `GET /api/files/:id/verify` | **已实现**（`verifyFile` 重新读字节算摘要） | 直接复用，正好用于"归档校验" | 摘要按同一算法、同一大小写 |
| `POST /api/devices/{id}/commands` + 回执 | **语义已有先例**：`route("POST", "/api/commands")`（`commandId` 幂等、`expectedRevision`、`replayed` 不重复广播） | 新增**设备维度**的命令接口；对象从 `session 实体` 换成 `device` | `commandId` 幂等、返回 `commandId` 但**不直接标成功**、重复提交返回同一结果、`409` 表示版本冲突 |
| `WS /ws/devices/{deviceId}` | `services/hub.mjs` 的 `new WebSocketServer({server, path:"/ws"})`（浏览器房间 + `kind:"event"` + `hello/lastSeq` + 20 s ping） | **必须新增一条设备通道**，不能复用 `/ws` 的房间语义（设备不是演示会话成员） | 保留它的好习惯：连上先补缺口、20 s ping 探活、`kind` 字段区分消息类型 |
| 操作员鉴权 | `services/auth.mjs`（HMAC 自校验令牌）+ `permissions.mjs`（按角色给权限） | 复用为**下发命令**的鉴权；设备令牌是**另一套**（不参与角色模型） | 401 = 未登录/令牌无效；403 = 权限不足（设备令牌不能下发命令） |
| `POST /api/devices/register` | 无 | **新增** | 返回 `heartbeatIntervalMs`/`offlineAfterMs`/`configVersion`/`demoSessionId`/`platformTime`，字段名照抄 |
| `POST /api/device-events/batch` | 无（现有 `GET /api/events` 是读历史事件） | **新增**，按 `messageId` 去重 | 至少一次投递 + 幂等去重；`accepted`/`duplicated` 是 messageId 列表 |
| `POST /api/batches` | 平台 PRD §14.2 的 `POST /scan-batches` / `POST /scan-batches/{id}/complete` | **新增**（或适配到 scan-batches） | `complete:false` = 部分接收，未完成不得进入整批分析 |
| `GET /api/artifacts/{id}/manifest`、`POST /api/artifacts/{id}/receipts` | 平台 PRD §14.2 的 `POST /packages/{id}/deliver`、`POST /deployments/{id}/receipt` | **新增**设备侧视图；产物表可复用 `packages/deployments` | `artifactKind=demo_nonflashable` + `demoOnly=true` 时禁止烧录；回执按 `commandId` 幂等；版本要**读回**再报 |
| `POST /api/devices/{id}/preview` | 无（平台 PRD §9.3 只说预览可下采样） | **新增** | 预览不作为原始图像归档；原图仍在批次目录 |
| `GET /api/health` | **已实现**（`{auth:false}`） | 直接复用 | 终端只用它测延迟与可达性 |

**路径规范差异**：平台 PRD §14.2 用 `/api/v1/...` 前缀 + `PUT /uploads/{id}/chunks/{n}`（片序号），
手持端 PRD §7.4 用 `/api/...` 无版本前缀 + `PUT /api/files/uploads/{id}/chunks`（偏移在参数里）。
两套需要一个适配层或一次统一；若走适配层，**消息语义、ID 与错误规则必须一致**（PRD §7.4 最后一句）。

## 7. 契约歧义与不一致清单（写文档时逐条核对出来的，未改平台代码）

| # | 位置 | 现象 | 本文档的取值 / 建议 |
|---|---|---|---|
| 1 | `POST /api/device-events/batch` 响应 | PRD 只写 `{accepted, duplicated, rejected}`，没说 `accepted`/`duplicated` 是**计数**还是 **messageId 清单**；终端 `platform_client._post_events_batch()` 当**清单**用（`list(body.get("accepted"))` 后 ack 这些 ID） | 取**清单** + 另附 `acceptedCount`/`duplicatedCount`。真平台若返回计数，终端 ack 会失效 |
| 2 | 分片偏移的位置 | PRD 只说"校验偏移"；终端 `put_chunk()` 用 `X-Chunk-Offset` 头，平台 PRD §14.2 用路径里的片序号 `/chunks/{n}` | 两者都接受（`?offset=` 优先）；真平台应二选一并写进文档 |
| 3 | 命令帧结构 | PRD §8.1 只列字段，没说放顶层还是 `payload` 内；终端 `_handle_inbound()` 只把 `payload` 交给 `on_command` | 顶层为权威值，同时镜像进 `payload`（见 §1.2） |
| 4 | 心跳消息类型 | PRD 给了 `heartbeatIntervalMs`/`offlineAfterMs`，没说心跳消息叫什么 | 终端用 `device.health`（`heartbeat:true` + `platformLatencyMs`）；平台应把它当已知类型并刷新 `lastSeenAt` |
| 5 | 预览图编码 | PRD 说"multipart 或 `application/octet-stream` + `X-Frame-Index`，自己定一种" | 本文定：裸 JPEG + `X-Frame-Index` 必有头（也接受 `Content-Type: image/jpeg`） |
| 6 | 设备令牌放哪 | PRD 只说"使用设备token认证"；终端 HTTP 用 `X-Device-Token`（还额外发 `Authorization: Bearer <设备令牌>`），WS 只能走查询串 `deviceToken` | 模拟平台四种都认；真平台应只认一种。注意**令牌进 URL 会被代理/访问日志记下来**，建议 WS 优先用头或 subprotocol |
| 7 | `deviceId` 是否必须在请求体 | 终端在创建上传/批次提交/事件补传里**不带** deviceId（只在 URL、事件信封或令牌里） | 模拟平台按 §4.1 顺序推断；真平台要么强制显式传，要么明确"从令牌推断并校验一致性" |
| 8 | `fileIds` 元素类型 | 终端 `app.submit_batch()` 发**对象数组** `{fileId, role, path, sha256, bytes}`；PRD 只写 `fileIds` | 两种都接受（字符串 / 对象）；真平台需明确 |
| 9 | `datasetHash` 算法 | PRD 没定义算法，只提到"两端共用一个 hash" | 采用终端 `storage.commit_manifest()`：按 `path` 字典序拼 `path\0sha256\n`（不含 `manifest.json`）取 sha256。建议写进正式契约 |
| 10 | 文件角色词表 | PRD §9.2 示例用 `radar`/`image`；终端实际用 `frames`/`segments`/`marks`/`quality`/`image`/`config`/`dataset`/`plan`/`events`/`marks_csv`/`image_index`/`batch` | 模拟平台合并两份词表，未知名归 `other` 不拒收；建议出一张统一角色表 |
| 11 | 路径规范 | 平台 PRD §14.2 是 `/api/v1/...` + `/uploads/{id}/chunks/{n}`；手持端 PRD §7.4 是 `/api/...` + `/api/files/uploads/{id}/chunks` | 需要一个适配层或统一一次；不要两端各写一套 |
| 12 | 响应包装 | 平台 PRD §14.1 要求 `{data, request_id, server_time}` 包装；手持端 PRD §7.4 是平铺字段 | 本文按手持端**平铺**（另给 `platformTime`）。适配层若加包装，终端要同时改 |
| 13 | 旧 `POST /api/files` 能力 | 现有平台只有一次性裸 body 上传（`?name=`），无分片、无摘要校验、无幂等 | **不能**把终端的分片协议直接打到旧路径上；必须在适配层实现偏移与摘要语义 |
| 14 | 产物回执的幂等键 | URL 已带 `artifactId`，但幂等按 `commandId` | 同 commandId 出现第二个 artifactId 时，模拟平台返回第一次的回执；真平台建议显式 `409` 拒绝这种组合 |
| 15 | `expiresAt` 的比较基准 | 设备时钟未校准（PRD §7.3 明确不能用设备时间算时延），却要用设备判断命令是否过期 | 平台在 register/hello/各响应里都给 `platformTime`；终端以"最近一次平台时间 + 本地单调增量"估平台时钟做判定 |
| 16 | `subprotocol: auth.<token>` | RFC6455 的 subprotocol 是给应用协议协商用的，把令牌塞进去是自定义约定 | 已实现，但建议真平台优先用查询串/头，避免与将来真正的子协议协商冲突 |
| 17 | 设备维度的操作员权限 | 现有 `permissions.mjs` 是按演示会话/角色给的，没有"能否给某台设备下发命令"这一项 | 需要新增权限项（如 `device.command`），否则任何登录用户都能给设备发暂停/更新命令 |
| 18 | `/api/health` 的 `service` 字段 | 真平台是 `mumai-shared`，模拟平台是 `mock-platform` | 终端只按 `ok`/可达性判断，**不要**按 `service` 值分支 |
| 19 | 离线阈值来源 | PRD 说阈值由配置决定，同时 register 又返回 `offlineAfterMs` | 以平台返回值为准（终端 `app.start()` 已用返回值覆盖本地默认），本地配置只作首连前的兜底 |
| 20 | 设备令牌轮换 | PRD §7.2 只要求配置里有 `deviceToken`，没有轮换协议 | 模拟平台给了"新令牌 + 旧令牌宽限期"的最小模型（控制台 `rotatetoken <deviceId>`）；真平台应明确重叠窗口与吊销方式，否则轮换当天必然掉线 |
| 21 | `device.selfcheck` 与永久拒收标记 | 终端会发 `device.selfcheck`（自检报告）。早期 `contracts.EventType` 里没有它，而平台按未知类型处理时**只回 reason、不回 messageId**，终端既 ack 不掉也删不掉，实测每 0.5 秒重推一次 | **已定案（两侧都改了）**：① `device.selfcheck` 正式写入 `contracts.EventType`；② `rejected` 每条必须带 `messageId` 与 `retryable`；③ 平台保证每个收到的 messageId 最终进 `accepted` 或 `rejected` 之一。终端的处理是：`retryable=false` → 出队不再重试；`retryable=true` 或缺省 → 保留并退避重试。模拟平台用 `--reject-extra-types` 可演示"平台暂不支持"这条路径 |
| 22 | `POST /api/devices/{id}/commands` 的 `expiresAt` 入参 | PRD 只把 `expiresAt` 定义为命令字段，没说能否由调用方指定（模拟平台支持直接传 `expiresAt`，用于下发"已经过期"的命令来验证拒执） | 联调 H08 时很有用；真平台若只允许 `ttlMs`，就把它当作平台侧内部字段，不要暴露给调用方 |

## 8. 模拟平台的调试扩展与故障注入

以下**只是模拟平台为了联调方便提供的**，真平台不必实现：

| 开关/接口 | 作用 |
|---|---|
| `--fail-register` | 注册一律 503 `REGISTER_REJECTED`（验证终端退避重试） |
| `--reject-checksum` | 每次 complete 前翻转服务端落盘文件 1 字节 → 必然 `422 CHECKSUM_MISMATCH` |
| `--drop-after-bytes N` | 单次上传累计收到 N 字节后直接掐断 TCP（验证断点续传与部分接收） |
| `--latency-ms N` | 每个请求前额外延迟 N 毫秒（验证超时/离线判定与 `platformLatencyMs`） |
| `--preview-keep N` | 每台设备保留最近 N 张预览图 |
| `--device-token` / `rotatetoken` | 初始令牌 / 运行时轮换（旧令牌留宽限期） |
| `GET /api/devices`、`GET /api/devices/{id}/state` | 调试视图（设备、遥测、命令与回执、上传、预览） |
| stdin 调试控制台 | `help` / `devices` / `telemetry <id>` / `state <id>` / `uploads <id>` / `batches` / `cmd <id> <type> [args]` / `expire <id>` / `artifact <id>` / `rotatetoken <id>` / `faults` / `quit` |

启动、控制台与日志的用法见 `F:\1\pi5\docs\平台接入教程.md`。
