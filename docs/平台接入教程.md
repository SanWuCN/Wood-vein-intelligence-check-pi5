# 木脉智检手持终端 · 平台接入教程

## 这份文档解决什么问题

树莓派手持终端（`python -m woodpulse`）已按 PRD v0.2 §7 / §8 实现主动连接、握手、心跳、遥测、
命令回执、分片上传与断点续传；**这套接口在现有平台 `server/` 里还不存在**。这份文档把"终端会发什么、
平台必须回什么"落成可执行步骤，供后端/集成同学照着改平台。

配套文件（都在 `F:\1\pi5`，本文事实来源）：

| 文件 | 作用 |
|---|---|
| `tools\mock_platform.py` | 本地模拟平台，字段与 `woodpulse\contracts.py` 同名，行为与 PRD 一致；支持故障注入与控制台 |
| `tools\smoke_mock_platform.py` | 端到端冒烟测试（自动起停模拟平台，正常路径 + 4 个故障注入） |
| `tools\integration_check.py` | 终端 ↔ 平台真实联动检查（真起终端、真发事件、真收命令、真回执） |
| `woodpulse\platform_client.py` | 终端侧唯一平台客户端；平台契约以它发的报文为准 |

> 命令的工作目录一律 `F:\1\pi5`。字段名一律 lowerCamelCase，以 `contracts.py` / `mock_platform.py` 为准；
> 终端内部 Python 属性是 snake_case，不要混进 JSON 契约。

### 1.4 五步验收

| 步骤 | 在哪做 | 命令 | 期望看到 |
|---|---|---|---|
| ① 设备在线 | 平台控制台 | `devices` | `handheld-02 online bootId=boot-... 最后上行=... 命令=0(未回执 0) 遥测=N 事件=M caps={...}` |
| ① 备选 | 另一终端 | `curl http://127.0.0.1:8080/api/devices/handheld-02/state` | JSON 含 `"connectionState":"online"`、`bootId`、`capabilities` |
| ② 遥测跳动 | 平台控制台 | `telemetry handheld-02` | 最后一条 `device.telemetry` 信封，`counters.telemetry` 持续增长（约 1 秒一条） |
| ③ 下发暂停 | 平台控制台 | `cmd handheld-02 pause_capture` | `已下发 cmd-xxxx type=pause_capture targetBatchId=None expiresAt=... delivered=True` |
| ④ 终端响应 | 终端界面/日志 | — | 采集页显示"平台请求暂停"，任务状态转"已暂停" |
| ⑤ 平台收到回执 | 平台控制台 | `state handheld-02` | 该命令 `receipt.state=executed`，`receipt.scope` 说明作用范围 |

> **③④⑤ 有一个前提：终端上要先"开始本次扫描"（任务进入"采集中"）。**
> 没有活动批次或任务不在 running 时，终端会**正确地**回 `failed` 而不是 `executed`：
> 没有活动批次 → `not_ready`（`reason=本机当前没有活动批次，无需暂停`）；任务停在"待开始/已结束" →
> `terminal_state`。这不是故障，是 PRD §8.1 要的语义：**只有真做完的动作才回 `executed`**。
> 所以现场演示的顺序是：终端开始扫描 → 平台控制台 `cmd handheld-02 pause_capture` → 终端当场停住并回 `executed`。
>
> 实测（真终端 app 连模拟平台）：`commandId=cmd-620d568b6c31` 在无活动批次时回
> `{"state":"failed","errorCode":"batch_mismatch","reason":"命令针对批次 scan-Z04-002，本机当前没有活动批次"}`，
> 而 `query_status` 同类命令回 `{"state":"executed"}` —— 三态回执是真在区分的。

控制台 `cmd` 真实输出（**示例输出**，这次设备未注册，故 `delivered=False`）：

```text
  已下发 cmd-46795762b0f1 type=pause_capture targetBatchId=None expiresAt=2026-09-12T16:12:47.880Z delivered=False
2026-09-12T16:07:47.880Z .. 命令 cmd-46795762b0f1（pause_capture）目标 handheld-02 不在线，已入队等重连（第 1 次投递尝试）
```

控制台命令全表（`HELP_TEXT`，实测原样）：`help`、`devices`、`telemetry <deviceId>`、`state <deviceId>`、
`uploads <deviceId>`、`batches`、`cmd <deviceId> <type> [参数..]`、`expire <deviceId>`、
`artifact <deviceId> [version]`、`rotatetoken <deviceId>`、`faults`、`quit`。
`expire <deviceId>` 把未回执命令的 `expiresAt` 改成过去并重推，用来验证"过期命令必须被拒"。

## 2. 三条数据通道的分工

PRD §7.1 定死三条通道，**不要互相替代**：

| 通道 | 承载 | 终端实现 | 特征 |
|---|---|---|---|
| WS `/ws/devices/{deviceId}` | 小消息：`device.*` / `capture.*` / `batch.*` / `config.*` / `command.*` / `update.*` / `system.*`，平台下行 `kind:"command"` | `platform_client.WebSocket` + `_pump()` | 文本帧 JSON、低延迟、平台按 `messageId` 去重 |
| HTTP | 样本/报告/更新包：`POST /api/files/uploads` → `PUT /chunks` → `POST /complete`、`POST /api/batches`、`GET /api/files/{id}/download`、`POST /api/artifacts/{id}/receipts` | `HttpClient` + `upload_file()` | 分片、断点续传、服务端重算摘要 |
| HTTP（低帧率） | 预览图 `POST /api/devices/{id}/preview` | `queue_preview()` + `post_preview()` | JPEG、约 1.5FPS、**不归档** |

**为什么不能把视频逐帧塞进事件日志**

1. 事件通道要的是**可去重的小消息**：平台按 `messageId` 去重（`ingest_envelope()` 命中 `seen_messages`
   直接返回 `"duplicated"`），信封还带 `seq`（同一 `bootId` 内单调递增）。逐帧视频没有稳定的
   `messageId → 一帧` 对应关系，重连补传根本无法判断"这帧收过没有"。
2. **outbox 会被打爆**：至少一次投递靠内存 outbox + SQLite `outbox` 表
   （`enqueue_event()` → `storage.enqueue_event()`）。掉线 10 分钟堆几十万条，
   而 `POST /api/device-events/batch` 单次上限 500 条（`h_device_events_batch`），补传退化成几百轮 HTTP。
3. **检索与保留策略不同**：事件是可查询的业务流水，视频是大字节资产（生命周期、冷热分层、对象存储）。
   混在一起等于让事件表承担 CDN 职责。
4. 遥测已经证明"允许丢中间样本"：`queue_telemetry()` 只保留最新一份，掉线期间不堆每秒 CPU 数据
   （PRD §8.2）。逐帧视频走这条通道只会被迫全量堆积或静默丢帧。

**为什么预览图不作为原始图像归档**（PRD §4.3 / §7.4）

预览是给人看现场画面的下采样 JPEG；归档图像走批次目录（`images/` + `frames.csv`），
由 `POST /api/batches` 的 `files[].role="image"` 声明并分片上传。模拟平台把这条规则做成硬约束：
必须带 `X-Frame-Index` 头（否则 422 `NO_FRAME_INDEX`）、≤2MiB（否则 413 `FRAME_TOO_LARGE`，
提示"预览应当下采样"）、必须是 JPEG（缺 `FF D8` → 422 `NOT_JPEG`）、
每台设备只保留最近 `--preview-keep`（默认 10）张并**真删文件**：

```text
.. 预览图只保留最近 10 张，已丢弃帧 [0, 1]（不作为原始图像归档，PRD §7.4）
```

真平台照做即可：预览目录是**环形缓冲**，不是资产库。

## 3. 设备身份与认证

### 3.1 五个 ID

| 字段 | 代表谁 | 生命周期 | 生成方 | 出现位置 |
|---|---|---|---|---|
| `deviceId` | **设备** | 长期，跨重启不变 | 部署时写进配置 | 注册体、WS 路径、每个信封、上传/批次推断 |
| `deviceToken` | 设备**凭证** | 长期，可轮换（旧令牌宽限期） | 平台签发 | `X-Device-Token` / `?deviceToken=` / `Authorization: Bearer` |
| `bootId` | **一次进程启动** | 每次 `python -m woodpulse` 换一个 | 终端启动时生成 | 注册体、WS 查询串、每个信封；平台靠它区分重启 |
| `actorId` | **操作人** | 按人，跨设备跨会话 | 真平台登录体系；终端侧 `operator_id`（默认 `rao`）/ `WOODPULSE_OPERATOR_ID` | 注册体 `operatorId`、下行命令 `actorId`、平台命令记录 `actorId` |
| `demoSessionId` | **排练轮次** | 一场排练一个 | 平台（模拟平台 `--session-id`；终端默认 `demo-01`） | 每个信封、WS 查询串、`payload.platformConfig` |

PRD §7.1 要求三者分开（设备 / 操作人 / 排练轮次）。实践后果：换人操作 → `deviceId` 不变 `actorId` 变；
换设备 → 反之；同一设备同一人第二轮排练 → 前两个不变 `demoSessionId` 变，**数据不能串场**。
排练轮次不一致时模拟平台"提醒但不覆盖"：

```text
.. 设备 handheld-02 连的是平台会话 demo-01，但查询串里写的是 demo-02（排练轮次不一致，注意别串场）
.. 设备 handheld-02 的 demoSessionId=demo-02 与平台会话 demo-01 不同（排练轮次隔离，不覆盖平台记录）
```

### 3.3 WS 令牌的三种携带方式

| 方式 | 谁在用 | 代价 |
|---|---|---|
| 查询串 `?deviceToken=`（模拟平台还认 `?token=`） | 终端 `_ws_url()` 一定带 | **令牌进 URL，会被 nginx/网关 access log、浏览器历史、代理缓存记下**；真平台必须脱敏 |
| 头 `X-Device-Token`（+ `Authorization: Bearer`） | 终端 HTTP 每次带；WS 握手也带 | 浏览器 WebSocket API 不能设自定义头，这条只对 Python 终端有效 |
| 子协议 `Sec-WebSocket-Protocol: woodpulse.v1, auth.<token>` | 模拟平台支持（取 `auth.` 之后），终端**目前不发** | 令牌不进 URL，生产环境推荐；平台要回 `Sec-WebSocket-Protocol: woodpulse.v1` |

模拟平台取令牌顺序（`_serve_ws()`）：`?deviceToken=` → `?token=` → `X-Device-Token` → 子协议 `auth.`。
**真平台只认一种并写进接口文档**（PRD §7.4 只说"用设备 token 认证"，没规定放哪）。

### 3.4 轮换与吊销

```text
mock> rotatetoken handheld-02
  新令牌：tok-e28e5dac3b74
  旧令牌在 60000ms 内仍可用；之后请让终端只带新令牌。
```

`rotate_token(new_token, grace_ms)` 把旧令牌过期时刻设为 `now + grace_ms`，新令牌长期有效；
`accept_token()` 对过期旧令牌返回 `False` → 401；宽限期由 `--token-grace-ms` 控制。

真平台要补三件事：① **新旧并存窗口**（否则现场要停机改配置）；② **吊销流程**（"后台点吊销立即失效"
与"轮换宽限期"是两条路径）；③ **鉴权失败留痕**——模拟平台会累加 `authFailures` 并记录 `lastAuthFailure`：

```text
!! 鉴权失败 /api/devices/register dev=handheld-02 token=demo-t… → 401
```

这两个字段在 `GET /api/devices/{id}/state` 里能查到，排查 401 最快。

### 4.2 每一步失败会看到什么

| 步骤 | 终端侧 | 平台侧日志/响应 | 缩小范围 |
|---|---|---|---|
| ② 网络不通 | `平台状态：离线 — 连接失败：...` | 无日志（请求没到） | `curl http://<平台>/api/health` |
| ② 令牌错 | 注册失败：`设备令牌无效：请检查 X-Device-Token...` | `!! 鉴权失败 /api/devices/register dev=... token=demo-t… → 401`、`status=401` | 比对 `--device-token` 与平台登记值 |
| ② 主版本不符 | 注册失败 | `422 UNSUPPORTED_SCHEMA（平台只认 1.0.x）` | 看 `contracts.SCHEMA_VERSION` |
| ② `--fail-register` | 退避重试 | `!! 注入故障 --fail-register：本次注册被拒（503，可重试）` | 去掉开关重启 |
| ③ 升级被拒 | `WebSocket 升级被拒绝：HTTP/1.1 401` | `status=401`（JSON 体） | 401 在 101 之前 ⇒ 令牌问题，不是协议问题 |
| ③ 非 WS 请求 | — | `426 UPGRADE_REQUIRED` | 浏览器直接访问即可看到 |
| ③ accept 不符 | `Sec-WebSocket-Accept 校验失败，对端可能不是 WebSocket 服务` | — | 中间代理改写响应，或平台没按 RFC6455 算 |
| ④ hello 没被认 | 无 hello 日志 | 回 `warning{code:"UNKNOWN_TYPE"}` | `--verbose` 看 `type=device.hello` 是否到达 |
| ⑤ 事件被拒 | `补传关键事件失败（N 条）`，outbox 不减 | `<< 补传事件 dev=... 共 N 条：入库 0 / 去重 0 / 拒收 N` | 看 `rejected[].reason`（第 6.6 节） |
| ⑦ 心跳测不到延迟 | 遥测 `platformLatencyMs: null` | `/api/health` 500 或被鉴权拦 | `/api/health` 必须允许无令牌访问 |
| ⑧ 命令没到 | 界面无"平台请求暂停" | `.. 命令 cmd-xxx（pause_capture）目标 handheld-02 不在线，已入队等重连（第 N 次投递尝试）` | `state <deviceId>` 看 `delivered` |
| ⑧ 命令过期 | `命令已于 ... 过期，设备拒绝执行` | 收到 `command.failed`，`errorCode=command_expired` | 控制台 `expire <deviceId>` 复现 |
| ⑨ 假活连接 | 迟迟不重连 | `!! 设备 ... 的 WS 连接 X 秒无任何帧，判定假活并关闭` | 阈值 `max(2*ws_ping_interval, 2*offlineAfterMs)` |

```js
route("POST", "/api/batches", async (ctx) => {
  const deviceId = resolveDeviceId(db, ctx);
  requireDevice(db, deviceId, ctx);
  const batchId = String(ctx.body.batchId ?? "").trim();
  if (!batchId) throw new WorkflowError(422, "NO_BATCH_ID", "缺少 batchId");

  const digest = sha256Hex(JSON.stringify(ctx.body));
  const previous = db.prepare("SELECT * FROM batches WHERE batch_id=?").get(batchId);
  if (previous && previous.digest !== digest) {
    throw new WorkflowError(409, "BATCH_CONFLICT", `批次 ${batchId} 已提交且内容不同，不允许原地改写`, { batchId });
  }
  // fileIds 认两种形状：字符串 fileId，或终端实际发的对象 {fileId, role, path, sha256, bytes}
  const received = [], unknownFileIds = [];
  for (const entry of ctx.body.fileIds ?? []) {
    const fileId = typeof entry === "string" ? entry : entry?.fileId;
    const file = fileId ? db.prepare("SELECT * FROM files WHERE file_id=?").get(fileId) : null;
    if (!file) { unknownFileIds.push(String(fileId ?? "")); continue; }
    received.push({ ...file, path: (typeof entry === "object" && entry.path) || file.name });
  }
  // “应当交付”= expectedFiles ∪ manifest.files[].path ∪ fileIds[].path，都没有才退回 PRD §9 必需清单
  const declared = collectDeclared(ctx.body);
  const pool = new Set(received.flatMap((f) => [f.name, basename(f.path)]));
  const missing = declared.filter((d) => !pool.has(d.name) && !pool.has(basename(d.name)))
                          .map((d) => ({ name: d.name, role: d.role, reason: "not_uploaded", source: d.source }));
  const actualDatasetHash = datasetHashOf(received);   // 按 path 字典序拼 path\0sha256\n，不含 manifest.json
  const complete = missing.length === 0 && unknownFileIds.length === 0;
  // 落库 batches / batch_files；complete=false 时**不得**进入整批分析（PRD §9.2）
  return {
    batchId, deviceId, accepted: true, complete, missing, unknownFileIds,
    receivedFiles: received.map(briefFile), receivedBytes: received.reduce((n, f) => n + f.size, 0),
    fileCount: received.length, batchState: complete ? "uploaded" : "partial",
    datasetHashMatch: ctx.body.datasetHash ? actualDatasetHash === ctx.body.datasetHash : null,
    datasetHash: ctx.body.datasetHash ?? null, actualDatasetHash,
    submittedAt: nowIso(), replayed: Boolean(previous),
  };
});
```

**其余接口的落点**（字段照抄 `mock_platform.ROUTES`）：

| 路由 | 方法 | 平台端要做什么 | 关键返回字段 |
|---|---|---|---|
| `/api/device-events/batch` | POST | 按 `messageId` 去重入库；单次 ≤500 条；`accepted`/`duplicated` **必须是 messageId 数组**而非计数，否则终端无法精确 ack | `accepted[]`, `duplicated[]`, `acceptedCount`, `duplicatedCount`, `rejected[{messageId, reason}]`, `receivedAt` |
| `/api/devices/{deviceId}/state` | GET | 运维视图：在线状态、最后遥测、命令与回执、计数器、鉴权失败 | `connectionState`, `bootId`, `lastSeenAt`, `capabilities`, `lastTelemetry`, `commands[]`, `lastReceipt`, `counters`, `authFailures` |
| `/api/devices/{deviceId}/preview` | POST | 低帧率预览：必须带 `X-Frame-Index`，≤2MiB，校验 JPEG 头，环形保留 N 张 | `frameIndex`, `bytes`, `sha256`, `receivedAt`, `keptFrames`, `retentionLimit` |
| `/api/artifacts/{artifactId}/manifest` | GET | 产物清单 | `artifactId`, `artifactKind`, `packageType`, `demoOnly`, `target`, `version`, `previousVersion`, `sha256`, `size`, `fileId`, `downloadUrl`, `contents` |
| `/api/artifacts/{artifactId}/receipts` | POST | 按 `commandId` 幂等；校验 `applyResult ∈ {applied, failed, skipped}`；校验 `sha256` 与登记一致 | `receiptId`, `applyResult`, `versionReadBack`, `acceptedAt`, `replayed` |
| `/api/files/{fileId}/download` | GET | 真实字节 + `X-File-Sha256` + `Accept-Ranges: bytes`（更新包要能续传） | 不返回 JSON，自己写响应流 |

### 5.2 鉴权与 deviceId 推断

设备面**不能复用** `actorFromRequest()`（那是人用的 HMAC 登录令牌）。加 `requireDevice(db, deviceId, ctx)`
校验 `X-Device-Token` / `?deviceToken=` / `Authorization: Bearer`；而 `POST /api/devices/:id/commands`
要**人令牌**：`auth: true` + `actorFromRequest(ctx.req)` 得到 `actorId`，再查 `permissionsOf(actor)`。

真实存在的坑：**终端在创建上传 / 提交批次 / 补传事件时请求体里不带 `deviceId`**
（`HttpClient.create_upload()` 的 body 只有 name/size/sha256/batchId/role/schemaVersion）。
所以平台必须能推断"这条请求说的是哪台设备"，顺序（`_resolve_device_id()`）：

1. 路径参数 → `X-Device-Id` 头 → body 的 `deviceId`；
2. 事件信封里的 `deviceId`（补齐传事件那一路）；
3. 用设备专属令牌反查；
4. 平台当前只注册了一台设备时就用它。

多台设备同时注册又都不显式给 `deviceId` → `422 NO_DEVICE_ID`，**明确报错而不是猜**。
更稳的做法是要求终端统一带 `X-Device-Id` 头。

### 5.3 设备通道 `/ws/devices/{deviceId}`

在 `server/index.mjs` 的 `createHub({server, db})` 之后加一条；新文件 `server/services/device_hub.mjs`
（**不要**改 `hub.mjs` 里 `/ws` 的行为）：

```js
import { WebSocketServer } from "ws";

const HEARTBEAT_MS = 5000;        // 下发给设备的心跳间隔（PRD §8.2）
const OFFLINE_AFTER_MS = 15000;   // 多久没上行判离线

export function createDeviceHub({ server, db }) {
  // ⚠️ 不能写成 `new WebSocketServer({ server, path: "/ws/devices" })`：
  //    ws 的 `path` 是**精确匹配**（hub.mjs 里 `path:"/ws"` 正是靠这个），
  //    而设备路径带 deviceId 后缀（/ws/devices/handheld-02），精确匹配永远不成立。
  //    所以用 noServer + 自己在 server 的 upgrade 事件里按正则分流。
  const wss = new WebSocketServer({ noServer: true });
  const online = new Map();       // deviceId → { socket, bootId, lastSeen }

  server.on("upgrade", (request, socket, head) => {
    const url = new URL(request.url, "http://localhost");
    const matched = /^\/ws\/devices\/([^/]+)$/.exec(url.pathname);
    if (!matched) return;                 // 不是设备通道：交给 hub.mjs 的 /ws 处理，别抢
    const deviceId = decodeURIComponent(matched[1]);
    // 令牌：查询串（终端写法）→ 头 → 子协议 auth.<token>
    const token =
      url.searchParams.get("deviceToken") ??
      url.searchParams.get("token") ??
      request.headers["x-device-token"] ??
      (request.headers["sec-websocket-protocol"] ?? "").split(",")
        .map((s) => s.trim()).find((p) => p.startsWith("auth."))?.slice(5);

    if (!verifyDeviceToken(db, deviceId, token)) {
      // 401 必须在 101 之前：终端要能区分“握手被拒”和“连上后被踢”
      socket.write("HTTP/1.1 401 Unauthorized\r\ncontent-type: application/json\r\n\r\n" +
        JSON.stringify({ code: "UNAUTHORIZED", message: "设备令牌无效", fieldErrors: [], retryable: false }));
      socket.destroy();
      logAuthFailure(db, deviceId, token, url.pathname);
      return;
    }
    wss.handleUpgrade(request, socket, head, (ws) => {
      wss.emit("connection", ws, request, deviceId, url);
    });
  });

  wss.on("connection", (socket, request, deviceId, url) => {
    const bootId = url.searchParams.get("bootId") ?? null;
    const demoSessionId = url.searchParams.get("demoSessionId") ?? null;
    if (demoSessionId && demoSessionId !== DEFAULT_SESSION_ID) {
      console.warn(`[device-ws] 设备 ${deviceId} 连的是会话 ${DEFAULT_SESSION_ID}，查询串写的是 ${demoSessionId}`);
    }
    online.set(deviceId, { socket, bootId, lastSeen: Date.now() });
    touchDevice(db, deviceId, bootId);

    // hello：通道参数给终端（终端读 payload.platformConfig）
    const platformConfig = {
      heartbeatIntervalMs: HEARTBEAT_MS, offlineAfterMs: OFFLINE_AFTER_MS,
      configVersion: currentConfigVersion(db), demoSessionId: DEFAULT_SESSION_ID,
      commandTtlMs: 300000, chunkSizeHint: 262144, previewKeep: 10,
    };
    socket.send(JSON.stringify({
      kind: "hello", schemaVersion: "1.0", deviceId, bootId, demoSessionId: DEFAULT_SESSION_ID,
      heartbeatIntervalMs: HEARTBEAT_MS, offlineAfterMs: OFFLINE_AFTER_MS,
      configVersion: platformConfig.configVersion, platformTime: new Date().toISOString(),
      pendingCommandCount: pendingCommands(db, deviceId).length,
      note: "设备通道已就绪；遥测/事件/回执走此通道，样本与更新包走 HTTP",
      payload: { platformConfig },
    }));

    // 至少一次投递：重连后重推“没回执、没过期”的命令（终端按 commandId 幂等）
    for (const command of pendingCommands(db, deviceId)) socket.send(JSON.stringify({ kind: "command", ...command }));

    socket.on("message", (raw) => {
      let envelope;
      try { envelope = JSON.parse(raw.toString("utf8")); } catch { return; }
      const record = online.get(deviceId);
      if (record) record.lastSeen = Date.now();     // 可能已被 sweeper 摘掉，别裸取 .lastSeen
      if (envelope.deviceId && envelope.deviceId !== deviceId) return;         // 只收本设备的
      if (String(envelope.schemaVersion ?? "1.0").split(".")[0] !== "1") {     // 未知主版本拒收
        socket.send(JSON.stringify({ kind: "warning", code: "UNSUPPORTED_SCHEMA", messageId: envelope.messageId }));
        return;
      }
      if (envelope.messageId) {
        if (seenMessage(db, envelope.messageId)) return;                       // 补传去重
        markMessageSeen(db, envelope.messageId, deviceId);
      }
      if (envelope.type === "device.telemetry") return saveTelemetry(db, deviceId, envelope);
      if (envelope.type === "device.health") return touchDevice(db, deviceId, bootId);
      if (envelope.type === "device.capabilities") return saveCapabilities(db, deviceId, envelope.payload);
      // 回执三态：平台据此推进命令状态，绝不凭“发出”标成功
      if (String(envelope.type).startsWith("command.")) return saveReceipt(db, deviceId, envelope);
      saveDeviceEvent(db, deviceId, envelope);
    });
    socket.on("close", () => online.delete(deviceId));
    socket.on("error", () => online.delete(deviceId));
  });

  // 假活连接与离线判定：平台自己算，不等设备开口
  const sweeper = setInterval(() => {
    const nowMs = Date.now();
    for (const record of online.values()) {
      if (nowMs - record.lastSeen > HEARTBEAT_MS * 3) { record.socket.terminate(); online.delete(record.deviceId); continue; }
      try { record.socket.ping(); } catch { /* 下一轮 terminate */ }
    }
    markOfflineDevices(db, nowMs - OFFLINE_AFTER_MS);
  }, HEARTBEAT_MS);
  sweeper.unref?.();

  return {
    onlineCount: () => online.size,
    connectionState(deviceId) {
      if (online.has(deviceId)) return "online";
      const device = getDevice(db, deviceId);
      if (!device?.last_seen_at) return "offline";
      return Date.now() - Date.parse(device.last_seen_at) <= OFFLINE_AFTER_MS ? "degraded" : "offline";
    },
    /** 在线直接推；不在线入队等重连（返回是否至少送到一条连接） */
    pushCommand(deviceId, command) {
      const record = online.get(deviceId);
      if (!record) {
        console.log(`[device-ws] 命令 ${command.commandId}（${command.type}）目标 ${deviceId} 不在线，已入队等重连`);
        return false;
      }
      record.socket.send(JSON.stringify({ kind: "command", ...command }));
      markDelivered(db, command.commandId);
      return true;
    },
    close() { clearInterval(sweeper); wss.close(); },
  };
}
```

三条不能省：① **房间按 `deviceId`**，设备令牌校验在 101 之前（`noServer` + `upgrade` 分流，因为 `ws` 的 `path` 只做精确匹配）；② **连接建立时与 `pushCommand()` 都要
覆盖"没回执、没过期"的命令**；③ **平台自己判离线**（`/ws` 的 `socket.ping()` 只探活连接，
15s 判离线要按 `last_seen` 单独算；`mock_platform.housekeeping()` 每 2s 巡检，日志形如
`!! 设备 ... 已 N 秒无任何上行，超过 offlineAfterMs=15000，判为离线`）。

"命令必须返回 commandId 且不能直接标成功"落在三处：
① `POST /api/devices/:id/commands` 返回 **202** + `commandId` + `expiresAt` + `delivered`，
`note` 写明"平台不因发出就标成功"；
② 状态机只有 `issued → delivered → accepted → executed | failed`，`executed` 只能由
`command.executed` 事件驱动，**没有任何 HTTP 成功路径直接落 `executed`**；
③ `command.failed` 必须带 `errorCode`（`command_expired`/`revision_stale`/`batch_mismatch`/`unsupported`/
`not_ready`/`terminal_state`/`scope_limited`/`checksum_failed`/`io_error`）、`reason` 与 `scope`。

## 6. 常见坑

**6.1 不要用未校准的设备时间算传输时延。** 现象：平台用 `sentAt` 减自己的 `Date.now()` 得到时延，
抖动几百毫秒甚至负数（树莓派无 RTC 时 NTP 同步前漂移很大；PRD §7.3 明确禁止）。正确做法：
时延用平台 `receivedAt` 与自己收到那一刻，或用**心跳往返**——终端 `device.health.payload.platformLatencyMs`
就是它 `GET /api/health` 的往返毫秒（`_measure_latency()`）；设备 `sentAt` 只做**同机排序**
（配合 `seq` 与 `deviceMonotonicNs`），跨设备一律用平台时间。

**6.2 网卡速率 ≠ 本应用上传速率。** `network.txBytesPerSec` 是**整张网卡**字节计数差分
（含 SSH、系统更新、其它进程；接口重置会重建基线并上报 0，`reason="接口计数回退（重连或重置），
已重建差分基线，本次速率上报 0"`）；本应用上传看 `upload.confirmedBytes` / `pendingBytes`
（`contracts.UPLOAD_KEYS`）。**契约里没有 `upload.confirmedBytesPerSec` 这个字段**（我核对过
`contracts.py` 的 `UPLOAD_KEYS` 与 `telemetry.py` 的遥测组装）——要速率就在平台侧按两次
`confirmedBytes` 与 `receivedAt` 的差自己算，别在端上造新字段。

**6.3 能力字段必须来自启动检查，不能写死。** `contracts.CapabilityReport` 只接受
`live` / `replay` / `unavailable` / `preset`（`Capability.ALL`，非法值 `set()` 直接抛 `ValueError`），
由启动检查逐项判定并给出 `capabilityReasons`。实测值随机器变化：

```text
能力：{'camera': 'unavailable', 'radar': 'replay', 'imu': 'unavailable', 'battery': 'unavailable',
       'telemetry': 'live', 'gpu': 'unavailable', 'preview': 'unavailable'}
```

平台不要把"设备在线"推断成"所有通道正常"（PRD §7.2）；`capabilities` 变化时终端单发
`device.capabilities`（带 `changed` 列表）。`unavailable` 字段在遥测里必须是
`null` + `reason`（`contracts.null_field()`：`{value: null, supported: false, quality: "unavailable", reason}`），
**不许填 0 或随机数**。

**6.4 暂停的作用范围要写清楚。** 终端只停**本地采集任务与检测样例回放推进**；健康遥测、心跳、
事件通道继续跑。回执 `scope` 会写明（`app_state.command_scope()`，取自 `scenarios.PAUSE_SCOPE_NOTE`）：

```text
作用范围：本地采集任务与检测样例回放；健康遥测、心跳与必要的事件通道继续运行。真实雷达是否停止发射需专用驱动确认。
```

`failed` 必须带 `errorCode` + `reason`：`not_ready`（没有活动批次）、`terminal_state`（任务不在 running）、
`revision_stale`（`expectedTaskRevision` 不匹配）、`batch_mismatch`（`targetBatchId` 不是当前批次）、
`command_expired`（已过期）。**`scope_limited` 用于"只能部分生效"**——例如驱动层确认不了雷达发射是否真停，
就回 `failed` + `scope_limited` + `reason` 说明哪部分做不到，而不是回 `executed` 让平台误判。

**6.5 `result_only` 不能画成原始 ADC。** 没有真实毫米波回波（PRD §9），格式固定
`response-sequence-v1`（`contracts.SAMPLE_FORMAT`），来源必须标 `sourceMode`。`frames.csv` 列是
`frame_index, sample_index, amplitude, t_ms`（`FRAMES_CSV_COLUMNS`，即 `amplitude` 是**样例采样点/距离单元**，
不是 ADC 原始值），`segments.json` 的 `tNs` / `deviceMonotonicNs` 是设备单调时间，
**不标注木柱内部深度毫米值**（PRD §3.2），平滑动画值也不得当原始值存（PRD §3.4）。
平台按 `sourceMode` 分流：`live` 实采 / `replay` 样例回放 / `preset` 预制结果 / `unavailable` 无数据
（中文文案直接用 `SourceMode.LABEL`）。

**6.6 另外几条真实坑**

1. **过期命令必须拒绝**：`app_state.validate_command()` 检查 `expiresAt`（`expiresAt` 与 `expires_at`
   两种拼写都认），过期返回 `(False, COMMAND_EXPIRED, "命令已于 ... 过期，设备拒绝执行")`。
   平台侧不要"重推一次就当时效重置"：`housekeeping()` 每 2s 巡检把过期命令标 `expired=True`。
   复现：控制台 `expire <deviceId>`。
2. **同 `commandId` 必须幂等**：平台 `issue_command()` 命中已有 `commandId` 返回原记录
   （`_replayed=True`，响应 `replayed: true`）不重复下发；终端 `storage.save_receipt()` 用
   `ON CONFLICT(command_id, state)` 只更新不新增。尤其 `prepare_update` 与 `assign_task`
   绝不能让设备做第二次动作。
3. **`messageId` 去重是补传前提**：`ingest_envelope()` 命中 `seen_messages` 返回 `"duplicated"`；
   `POST /api/device-events/batch` 的 `accepted` / `duplicated` 都是"可 ack 的 messageId 列表"。
   **平台只返回计数时终端会退化成"按顺序确认前 N 条"并打 warning**
   （实测：`平台 /api/device-events/batch 返回的是计数而不是 messageId 数组，已按发送顺序确认前 N 条`）。
4. **分片 `offset` 语义是"下一个待写字节位置"，必须严格连续**：`offset < receivedOffset` 且磁盘字节一致
   → 200 `duplicated: true` 幂等，不一致 → 409 `CHUNK_CONFLICT`；`offset > receivedOffset` → 409 `OFFSET_MISMATCH`
   （`retryable: true`，带 `expected`/`actual`/`receivedOffset`/`size`）；`offset + len > size` → 422 `CHUNK_OVERRUN`。
   终端 `upload_file()` **收到 409 就清空 `uploadId` 从 0 重传**（`needs_recreate = status == 409`），
   所以 409 不能拿来表达限流。
5. **同摘要复用文件仍要建立业务关联**：平台已有同 `sha256` 时 `create_upload()` 返回
   `completed: true`、`reused: true`、`fileId` 指向已有文件、`receivedOffset=size`，
   但这次上传记录仍入库，批次提交时照常出现在 `receivedFiles` 里（PRD §9.2）。
   反之**同名 + 同批次 + 同角色 + 摘要不同 → 409 `UPLOAD_CONFLICT`**，不许静默覆盖。
6. **`datasetHash` 平台要重算**：两侧算法一致——按路径字典序拼 `path\0sha256\n`，**排除 `manifest.json`**。
   模拟平台只报告不拦截（`datasetHashMatch` / `actualDatasetHash` + 一行
   `!! 批次 ... 的 datasetHash 不一致`），真平台应把不一致当"整批不可信"。
7. **`fileIds` 匹配要同时按文件名与相对路径**：终端上传只传 basename，manifest 里写的是
   `images/frame_00000.png`；模拟平台把两边都放进匹配池，并取 `expectedFiles` ∪ `manifest.files[].path`
   ∪ `fileIds[].path` 的并集，三者都没有才退回 PRD §9 必需清单。只按 basename 会把"同名不同目录"判错。
8. **拒收必须带 `messageId` 与 `retryable`，否则终端要么无限重推、要么静默丢数据**（实测发现）。
   终端会发 `device.selfcheck`（`app.py` 的自检报告）。早期它不在任何白名单里，
   而平台按未知类型处理时**只回 `reason`、不回 `messageId`**，现象是：

```text
<< 补传事件 dev=handheld-02 共 1 条：入库 0 / 去重 0 / 拒收 1
（0.5 秒后又来一条一模一样的，永远不停）
```

   为什么严重：被拒的 `messageId` 既不在 `accepted` 也不在 `duplicated` 里，
   终端无法把它从 outbox 删掉，于是每 0.5 秒重推一次、永远不会自己停。

   **定案的做法（两侧都已实现）：**

   | 谁 | 做什么 |
   |---|---|
   | 终端 | `device.selfcheck` 已正式写入 `contracts.EventType`；收到 `retryable=false` 的拒收 → 直接出队；`retryable=true` 或缺省 → 保留并退避重试 |
   | 平台 | `rejected` 每条带 `messageId` + `reason` + `code` + `retryable`；**保证每个收到的 messageId 最终进 `accepted` 或 `rejected` 之一**，不得静默丢弃 |

   判断可重试性的口径：**重试多少次结果都一样 → `retryable=false`**（未知类型、主版本不符、
   deviceId 不符、信封不合法）；**过一会儿可能就好 → `retryable=true`**（平台队列满、过载）。
   拿不准就写 `true`：终端会多试几次；写 `false` 而实际是临时故障，那条业务数据就永久丢了。

   模拟平台提供两条路径来分别验证（响应里还有 `unaccounted` 字段做契约自检）：

```bash
python tools/mock_platform.py --port 8099                       # 收下 device.selfcheck（默认）
python tools/mock_platform.py --port 8099 --reject-extra-types   # 显式拒收 + retryable=false
```

   两条都实测过：拒收路径下终端立刻出队，之后静置 8 秒平台侧只再看到 `device.health`，
   没有 `device.selfcheck` 重推。

## 7. 联调故障排查清单

日志读法：`时间 方向 方法 路径 status dur dev`；`<<` 收、`>>` 发；WS 帧看 `frame=` 与 `type=`（后者需 `--verbose`）。

**7.1 连不上**

| 先看哪一行 | 怎么缩小范围 | 复现开关 |
|---|---|---|
| 平台完全没有日志 | `curl http://<平台IP>:<端口>/api/health`；确认 `--host 0.0.0.0`、防火墙放行；树莓派用横幅里的"局域网地址"而非 `127.0.0.1` | — |
| 有 `<<` 没有对应 `>>` | 请求进来了但处理卡住/崩了，看 stderr 的 traceback | `--latency-ms 500` 拉长耗时，确认是否超时（终端 `request_timeout_s=10.0`） |
| `>> ... status=401` | 令牌不一致；看 `state <deviceId>` 的 `authFailures` / `lastAuthFailure` | 用错令牌跑冒烟即可复现（`[PASS] 1b 令牌错误必须 401`） |
| `>> POST /api/devices/register status=503` | 平台在维护或注入开关没关 | `--fail-register` |
| 终端日志 `将在 N.Ns 后重连平台` | 退避在跑（1→2→4→…→20s，±25% 抖动），别急着判定故障 | `--fail-register` + `--latency-ms` |

**7.2 握手 401**

- 先看平台那一行：`!! 鉴权失败 /ws/devices/handheld-02 dev=handheld-02 token=demo-t… → 401`。
  令牌只打前 6 位（`mask_token()`），比对前缀就能确认是不是配错。
- 再分"握手被拒"还是"连上后被踢"：模拟平台在 **101 之前**回 401（JSON 体），终端报
  `WebSocket 升级被拒绝：HTTP/1.1 401 ...`；101 之后被关则是 `对端关闭了连接` / `连接中断`。
  排查方向完全不同（令牌 vs 业务）。
- WS 与 HTTP 令牌来源不同：HTTP 走 `X-Device-Token`，WS 走查询串（浏览器不能给 WS 设自定义头）。
  平台只认一种时，另一种必须显式拒绝并说明，别默默放行。
- 轮换期间：`rotatetoken <deviceId>` 后旧令牌在 `--token-grace-ms`（默认 60000ms）内仍可用；
  过宽限期必须 401。

**7.3 WS 被代理掐断**

| 现象 | 原因 | 处理 |
|---|---|---|
| 每 60s/30s 整点断一次，连上又断 | nginx/网关 `proxy_read_timeout` 到点关空闲连接 | 平台 5s 心跳（`heartbeatIntervalMs` 下发），代理超时 ≥3 倍心跳；确认 `proxy_set_header Upgrade/Connection` 已配 |
| `!! 设备 ... 的 WS 连接 X 秒无任何帧，判定假活并关闭` | 连接在但设备不说话（休眠/切网） | 阈值 `max(2*ws_ping_interval, 2*offlineAfterMs)`；用 `--ws-ping-interval` 调 |
| 只有 `heartbeat` 没有 `telemetry` | 不是代理问题，是终端侧线程/存储异常 | 见 7.5 |
| 抓包 TCP 在但没有 WS 帧 | 中间设备静默丢连接 | 双端都开 ping：平台 `--ws-ping-interval` + 终端 5s 心跳 |

**7.4 上传摘要不一致**

- 平台那一行：`>> PUT /api/files/uploads/up-xxx/chunks status=200` 之后
  `>> POST /api/files/uploads/up-xxx/complete status=422`，响应体 `code=CHECKSUM_MISMATCH` 带
  `expected` / `actual`，前 16 位一比就知道是"声明错了"还是"字节错了"。
- 分片级摘要：`PUT /chunks` 带 `X-Chunk-Sha256`，不一致回 422 `CHUNK_CHECKSUM_MISMATCH`
  （带 `offset`、`length`），比整文件 422 好定位得多。
- 复现开关 `--reject-checksum`：**真的把落盘字节翻转 1 字节**再重算摘要（不做假报 422），
  日志 `!! 注入故障 --reject-checksum：已在服务端翻转 1 字节，接下来 complete 必然摘要不一致
  （想成功就重启模拟平台去掉这个开关）`。
- 注意：声明摘要在平台**已存在**时会直接"复用已完成"，不走摘要比对（冒烟 3c）；
  测"摘要不一致"必须用平台没见过的新内容。
- 部分接收用 `--drop-after-bytes N`：第 N 字节后直接掐 TCP（不给响应），平台记 `receivedOffset=N` 并打
  `!! 注入故障 --drop-after-bytes=150：已接收 offset=150/200 后强行断开连接（不给响应）`；
  终端重建上传后应从 `receivedOffset=150` 续传（冒烟 F3 实测通过）。

**7.5 平台显示离线但终端在线**

1. **平台侧 `>>` 帧还在不在**：`devices` 里"最后上行"时间在跳 → 平台判离线逻辑错（阈值/时钟）；
   不跳 → 终端根本没发上来。
2. **是不是 `device.hello` 之后再无遥测**：日志停在 `++ 设备 handheld-02 设备通道已连接（1 条）` +
   `<< ... type=device.hello` 之后什么都没有，而平台因 WS 还在而显示在线 ⇒ 终端侧网络线程死了。
   这是"SQLite 跨线程"缺陷的原始现象（见 7.6，当前已修）。
3. **终端侧日志**：`平台状态：离线/延迟 — ...` 的 detail 会说明原因（`连接失败`、`连接中断`、
   `已 N 秒未收到平台消息`、`平台响应延迟（N 秒）`）。
4. **终端在线但平台判离线**：`offlineAfterMs=15000` 指"没有任何上行"；遥测 1s、心跳 5s，
   正常绝不触发。注意**被拒收的事件不算"没上行"**：WS 帧一到达就刷新 `lastSeenAt`
   （`WsSession.run()` 里的 `touch_device()`），所以判离线一定是真的断了，或者遥测压根没发出来
   —— 用 `telemetry <deviceId>` 与 `state <deviceId>` 的 `counters.telemetry` 确认平台确实收到了遥测。
5. `--latency-ms 120` 验证"网络慢但不掉线"：终端延迟阈值是 `heartbeat_interval_s * 2 = 10s`，
   15s 转离线。

**7.6 已知阻断项的核实结果（照着改代码前先看这里）**

> 任务交底时列出的两个阻断项，我逐个复核了**当前源码**，结论与交底不一致。如实写清楚，
> 避免照着过期结论去改已经修好的代码。

**① `storage.py` 的 SQLite 连接跨线程使用 —— 已修，不再是阻断项。**

- 交底时的原实现（当时的第 193 行）是
  `self._conn = sqlite3.connect(str(self.db_path), timeout=5.0, isolation_level=None)`：
  连接在**主线程**创建，而 `platform_client._loop` 按 PRD §10 跑在**网络工作线程**里，
  访问同一个连接会抛 `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread`。
- 当前实现已经改为"**每线程一个连接 + 写路径加锁**"：`Storage._connection()` 用 `threading.local()` 取当前线程连接，
  新建时执行 `PRAGMA journal_mode=WAL` / `busy_timeout=10000` / `foreign_keys=ON` 并跑幂等建表；
  `tx()` 用 `threading.RLock` 串行化写。类 docstring 还专门写了为什么"只加一个 `check_same_thread=False`
  是不够的"（多线程共用一个 cursor 出的是更隐蔽的错乱）。
- 原始现象（握手成功、`device.hello` 到了平台后再无遥测、平台还显示在线）是**真实历史缺陷**：
  `tools\integration_check.py` 的注释确认它"历史上抓出过"，而该脚本**实测全通过**。

**② `enqueue_event()` 只在重连时 flush、`_pump()` 没有周期 flush —— 已修，不再是阻断项。**

- 当前 `_pump()` 里有 0.5s 周期的刷出，并兼顾磁盘 outbox：

```python
# 关键业务事件（命令回执、capture.*、batch.*）在**正常连接期间**也要发出去。
# 只靠重连时补传是不够的：那样平台会一直看到“命令已下发但没有回执”，
# 而 PRD §8.1 的三态回执正是靠这些事件送达的。
if now - self._last_flush >= 0.5:
    self._last_flush = now
    if self.pending_events:
        self.flush_outbox()
    elif self.storage is not None and self.storage.pending_event_count():
        self._replay_stored_outbox(limit=50)
```

- 实测证据：一次 16 秒真实运行里平台持续收到 `type=device.telemetry`，下发 `pause_capture` 后能查到
  `receipt.state = executed`；`integration_check.py` 的 `[PASS] 回执 executed 到达平台` 与
  `[PASS] 关键事件正常连接期间送达 — events=36 最近一条=capture.progress` 就是这条修复的回归点。

**③ `device.selfcheck` 与"永久拒收"标记 —— 已修复（详见 6.6 第 8 条）**

原先它不在任何事件白名单里，平台按未知类型拒收时只回 `reason`、不回 `messageId`，
终端 ack 不掉 → 每 0.5 秒重推一次，持续占带宽、污染日志，自检结果也入不了平台库。

现在两侧都改了：`device.selfcheck` 写入 `contracts.EventType`；
`rejected` 每条带 `messageId` + `retryable`；平台保证每个收到的 messageId
最终进 `accepted` 或 `rejected` 之一。终端据此分流：

| 平台回执 | 终端行为 |
|---|---|
| `accepted` / `duplicated` | 从 outbox 出队 |
| `rejected` + `retryable=false` | **出队，不再重试** |
| `rejected` + `retryable=true`（或缺省） | 保留，按退避重试 |
| 什么都没回（静默丢弃） | 保留并重试，连续多轮后打一条指向契约的告警 |
